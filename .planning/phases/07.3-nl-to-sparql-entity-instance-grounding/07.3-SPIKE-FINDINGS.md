# Phase 07.3 Spike Findings — Entity/instance grounding

Two spikes were run **before** planning to pick the accuracy lever empirically rather than
by roadmap assumption. Both used the live `gpt-4o-mini` provider over the vendored CK25
49-case set, graded by the eval's **own** execution judge
(`tests/nl2sparql/eval/runner.py::_judge`, `judge: execution`). Prototypes + raw
reports/logs are preserved at **`scratchpad/nl-grounding-spike/`** (untracked, durable).

## Result 1 — Execution-guided selection is DEAD for CK25 (drop it)

`scratchpad/nl-grounding-spike/egs_spike.py`. Sample N=5 @ temp 0.7 → filter transpilable →
execute each vs the CK25 graph → plurality-vote answer-sets (MBR / self-consistency).

- Arm A baseline (zero-shot, repair=2): **4/49**. Arm B MBR: **5/49**. Δ +1 case,
  McNemar **p=1.0**, not significant.
- **Why:** 4.59/5 candidates transpile and FULL consensus forms in **90%** of cases — the
  model is confidently, *systematically* wrong; there is no correct sample to select and no
  variance to exploit. Transpilability (the owned validator) is non-discriminating.
- This retires the former v1.1 "execution-guided selection" lever for the corporate domain.

## Result 2 — Entity/instance grounding DOUBLES CK25 (this phase)

`scratchpad/nl-grounding-spike/grounding_spike.py`. Both arms single-sample, temp 0, so the
ONLY variable is an injected "Known entities (use these EXACT IRIs)" block.

- Arm N (no grounding): **6/49 (12.2%)** — reproduces the committed baseline exactly.
- Arm G (grounding): **12/49 (24.5%)**.
- Δ **+12.2pt**, 95% CI **[+4.1, +22.4]**, McNemar **b=6 / c=0, p=0.031, ZERO regressions**.
- Retrieval: label index over `rdfs:label|pv:name` (2618 instances), top-k=20 by
  label-token substring match; **gold-IRI retrieval recall = 24/25 (0.96)** (one miss is a
  question typo "pontiometer"→Potentiometer).

### Reference design (proven, ready to productionize)
1. **Index:** one entry per instance IRI → {label strings, type}, from the target graph.
2. **Retrieve:** per question, top-k entities whose label tokens appear (substring, either
   direction to survive plural/inflection) in the question.
3. **Inject:** a prompt block of `<IRI> — "label" (type)` + an instruction to use the exact
   IRI directly rather than matching a name literal.
4. **Where it lives:** a language-agnostic seam in `arango_query_core.nl` (engine-side), so
   the Cypher repo inherits it. Retrieval targets the request's instance data / a
   schema-agnostic index — never CK25-specific curation — so it transfers to CDF unchanged.

## What grounding does NOT fix (explicitly out of scope — later phases)

Of the 37 remaining CK25 failures:
- **Schema-convention / modeling gaps** (~15 cases had the gold IRI retrieved but still
  failed): e.g. "manager of the Data Services dept" → model does `dept pv:hasManager ?x`
  (empty; `hasManager` domain is Employee) vs gold's indirection
  `?p pv:memberOf dept ; ?p pv:hasManager ?result`; also `subClassOf*`, OPTIONAL for
  optional attrs. → **in-domain few-shot** (teach idioms, not answers) is the fix.
- **Judge projection-shape strictness**: e.g. model returns `?agent ?name`, gold returns
  `?result` — same entities, but the answer-set judge keys on ALL projected columns, so an
  extra correct column scores as fail. Some true accuracy is **deflated by the instrument**.
  → a separate eval-quality task (loosen projection tolerance).

## Planning notes / invariants
- Gate on a **significant** CK25 lift (McNemar p<0.05, 0 regressions), not just Δ>0.
- Consider a small power/MDE note (n=49) as 07.1/07.2 did.
- Non-regression (hard): W3C DAWG ≥96.4%; transpiler package untouched; scripted = CI
  default (no live calls in CI); eval sets independently reported.
- Prototype scripts import `_judge`/`_build_label_map`/`_execution_row_key` from the runner
  and `oxi_query` from `tests/helpers/oxi.py` — reuse those, don't re-derive judging.
