# Phase 07.3: Code Review Report

**Reviewed:** 2026-07-24T14:31:35Z
**Depth:** standard
**Files Reviewed:** 13
**Status:** issues_found

## Summary

Phase 07.3 wires entity/instance grounding (seam 6) through `SparqlAdapter` /
`SparqlLanguageAdapter` / `NlPipeline` into the shared `NLQueryEngine`, and adds
an eval-only `build_label_index()` helper (`tests/nl2sparql/eval/grounding_index_builder.py`)
that turns CK25's vendored Turtle instance graph into a `LabelIndex` for the
harness. The seam-wiring code (`adapter.py`, `engine_adapter.py`, `pipeline.py`)
is small, additive, and mirrors the existing `few_shot_index` precedent
correctly — the packaging boundary (pyoxigraph stays test-only, imports kept
function-local) and the "dynamic per-question, never in the static/cacheable
grammar prefix" invariant are both upheld and test-covered
(`test_grounding_engine_prompt.py`).

However, direct execution of the new `grounding_index_builder.build_label_index()`
against the actual vendored CK25 data (`tests/nl2sparql/eval/vendored/ck25/raw/prod-inst.ttl`)
surfaces two BLOCKER-level correctness bugs that are **not caught by any
existing test** (the only test touching this file, `test_grounding_recall.py`,
checks gold-IRI retrieval *recall* only, never precision/purity of what gets
retrieved). Both were confirmed empirically against the real vendored corpus,
not just by code inspection (see reproduction commands in each finding). Given
this exact, buggy index is what produced the phase's headline NL-ACC-01
confirmatory-test numbers in `baseline.json`
(`openai-gpt4o-mini-ck25-grounded.confirmatory_test`), these are data-quality
defects in the evidence this phase reports, not just latent risk.

## Critical Issues

### CR-01: Grounding index leaks ontology-level classes/properties into the "Known entities" prompt as if they were groundable instances

**File:** `tests/nl2sparql/eval/grounding_index_builder.py:64-68`

**Issue:** `build_label_index()`'s SPARQL query has no filter restricting `?s`
to instance-level individuals:

```python
query = f"""
SELECT ?s ?label ?type WHERE {{
  ?s ({predicate_union}) ?label .
  OPTIONAL {{ ?s a ?type }}
}}"""
```

CK25's `raw/prod-inst.ttl` embeds its OWL vocabulary header (class/property
definitions, each carrying its own `rdfs:label`) in the *same file* as the
instance data. Because the query matches "any subject with `rdfs:label` or
`pv:name`," it pulls in every ontology term (`pv:Manager`, `pv:hasManager`,
`pv:email`, `pv:name`, `pv:Department`, `pv:Supplier`, …) as a `GroundedEntity`
alongside real named individuals (`prod-instances/empl-Heinrich.Hoch@…`).

Confirmed by direct execution against the real vendored corpus: 45 of the
2618 indexed "entities" are schema terms, and **43 of the 49 CK25 corpus
questions (88%) retrieve at least one schema-level IRI** into the "## Known
entities (use these EXACT IRIs)" block — 173 of 786 total retrieved slots
(22%) across the corpus are schema noise, not instance data:

```
$ .venv/bin/python -c "
from tests.nl2sparql.eval.grounding_index_builder import build_label_index
from pathlib import Path
import yaml
data_ttl = Path('tests/nl2sparql/eval/vendored/ck25/raw/prod-inst.ttl').read_text()
idx = build_label_index(data_ttl, ['rdfs:label', 'pv:name'])
corpus = yaml.safe_load(Path('tests/nl2sparql/eval/vendored/ck25/corpus.yml').read_text())
polluted_ids = {e.id for e in idx._entities if any(chr(34) in lab for lab in e.labels)}
cases_with_pollution = sum(1 for c in corpus['cases'] if any(e.id in polluted_ids for e in idx.retrieve(c['nl'], k=20)))
print(cases_with_pollution, '/', len(corpus['cases']))
"
43 / 49
```

This directly contradicts the seam's own documented purpose ("The question
may refer to specific named individuals/things below" —
`engine_adapter.py:258-261`, `adapter.py:118-121`) and the prompt actively
instructs the model to bind these class/property IRIs "directly in your
query ... instead of matching on a name literal," which is semantically wrong
for a class/property IRI and risks hallucinated/incorrect bindings. This is
the exact index used to produce the `openai-gpt4o-mini-ck25-grounded` numbers
folded into `baseline.json`, so the phase's confirmatory evidence for
NL-ACC-01 was measured with this noise present.

**Fix:** Exclude ontology-level subjects from the query, e.g.:

```python
query = f"""
SELECT ?s ?label ?type WHERE {{
  ?s ({predicate_union}) ?label .
  FILTER NOT EXISTS {{ ?s a <http://www.w3.org/2002/07/owl#Class> }}
  FILTER NOT EXISTS {{ ?s a <http://www.w3.org/2002/07/owl#ObjectProperty> }}
  FILTER NOT EXISTS {{ ?s a <http://www.w3.org/2002/07/owl#DatatypeProperty> }}
  OPTIONAL {{ ?s a ?type }}
}}"""
```

or, more robustly, load the ontology/vocab file and the instance file into
separate stores/graphs and only build the index from the instance store.

### CR-02: Label literal-stripping order corrupts language-tagged labels (`"@en` artifact leaks into the LLM prompt)

**File:** `tests/nl2sparql/eval/grounding_index_builder.py:76`

**Issue:**

```python
label = (row.get("label") or "").strip('"').split('"^^')[0]
```

This strips leading/trailing `"` characters **before** splitting off the
`^^<datatype>`/`@lang` suffix. For a plain literal (`"Alice"`) this happens to
work, but for a language-tagged literal (`"Manager"@en`, as pyoxigraph
stringifies every `rdfs:label` triple in CK25's vendored ontology header),
`str.strip('"')` only removes the leading quote (the string's *last*
character is `n`, not `"`), leaving `Manager"@en` — the trailing `"@en`
survives into the `GroundedEntity.labels` tuple and is rendered verbatim into
the "Known entities" prompt block shown to the LLM.

This is a straightforward order-of-operations bug: the correct order (split
the suffix off first, *then* strip quotes) is already implemented correctly
elsewhere in this exact file/phase, `tests/nl2sparql/eval/runner.py:347-352`
(`_strip_execution_literal`):

```python
def _strip_execution_literal(raw: str) -> str:
    return raw.split('"^^')[0].strip('"').split('"@')[0]
```

Confirmed by direct execution against the real vendored data — every one of
the 45 schema-level entities from CR-01 renders with a corrupted label, e.g.
`http://ld.company.org/prod-vocab/hasManager` → `'has manager"@en'` instead of
`'has manager'`. (Once CR-01 is fixed this specific manifestation disappears
for CK25, but the bug is general — any dataset whose instance-level labels
carry a language tag, e.g. a future CDF corpus, would hit the same corruption
on real, in-scope entities.)

**Fix:** Mirror `_strip_execution_literal`'s order:

```python
label = (row.get("label") or "").split('"^^')[0].strip('"').split('"@')[0]
```

## Warnings

### WR-01: `_PREFIXES` hardcodes only CK25's own vocabulary prefixes, contradicting the "transfers to CDF unchanged" design claim

**File:** `tests/nl2sparql/eval/grounding_index_builder.py:28-32, 41-46`

**Issue:** `runner.py`'s comment (lines 544-547) states the grounding
mechanism's `label_predicates:` config is meant to be the *only* place a
dataset-specific predicate lives ("never hardcoded here (Pitfall 2)") so the
mechanism "transfers to CDF unchanged." But `_expand_predicate` can only
resolve a *prefixed* predicate (e.g. `"pv:name"`) against the fixed
`_PREFIXES` dict (`rdfs`, `pv`, `prodi` — CK25's own vocab/instance
namespaces). A future corpus (CDF or otherwise) that lists a
prefixed predicate under a *different* prefix in its `grounding.label_predicates:`
config would raise `ValueError: unknown label predicate prefix` — requiring a
code change to this file, not just a config edit, contradicting the stated
portability goal. (It fails loudly rather than silently, which limits the
severity, but the design goal itself is not met.)

**Fix:** Either require `label_predicates:` to always use full IRIs (drop
prefix support entirely, simplifying `_expand_predicate`), or thread the
prefix→IRI map itself through the `grounding:` config block instead of
hardcoding it in this file.

### WR-02: Duplicate `grounding_prompt_section` wording across two adapters with no test enforcing byte-identity

**File:** `arango_sparql/nl2sparql/adapter.py:110-125`, `arango_sparql/nl2sparql/engine_adapter.py:244-265`

**Issue:** Both `SparqlLanguageAdapter.grounding_prompt_section` and
`SparqlAdapter.grounding_prompt_section` are verbatim-duplicated
implementations, and both docstrings explicitly warn "do NOT paraphrase;
rephrasing invalidates the measured lift" — i.e. the two copies must stay
byte-identical forever. Nothing enforces this: `tests/nl2sparql/test_adapter.py`
exercises only `SparqlLanguageAdapter`, and `tests/nl2sparql/test_grounding_engine_prompt.py`
exercises only `SparqlAdapter`. A future edit applied to one file (e.g. a typo
fix, or a wording tweak prompted by a new spike) can silently diverge from
the other without any test failing.

**Fix:** Add a small cross-adapter parity test (construct both adapters with
the same `LabelIndex`/question fixture and assert their
`grounding_prompt_section` outputs are equal), or factor the shared
`header`/`instruction`/`id_prefix`/`id_suffix` constants into one module both
adapters import from.

### WR-03: No unit test exercises `build_label_index`'s query/normalization logic directly — only end-to-end recall is asserted

**File:** `tests/nl2sparql/eval/test_grounding_recall.py` (whole file), `tests/nl2sparql/eval/grounding_index_builder.py`

**Issue:** The only test touching `build_label_index`
(`test_gold_iri_retrieval_recall_meets_spike_floor`) asserts gold-IRI
retrieval *recall* (≥ 0.90) and passes today (0.96) even with both CR-01 and
CR-02 present, because the real named individuals the recall test checks for
still out-rank the schema noise. There is no assertion on *precision/purity*
of the built index (e.g. "no retrieved entity's `type` is `owl:Class`/
`owl:ObjectProperty`/`owl:DatatypeProperty`") nor on label cleanliness (no
stray `"`/`@lang` remnants) — exactly the gap that let CR-01/CR-02 ship
undetected.

**Fix:** Add a small, deterministic unit test against a hand-rolled Turtle
fixture (mirroring `test_grounding_engine_prompt.py`'s `_build_index()`
pattern, but built through `build_label_index` itself) asserting that (a) a
class/property subject with `rdfs:label` is excluded from the resulting
`LabelIndex`, and (b) a language-tagged (`@en`) and a datatype-tagged (`^^xsd:...`)
label both normalize to clean text with no `"`/`@lang`/`^^` remnants.
