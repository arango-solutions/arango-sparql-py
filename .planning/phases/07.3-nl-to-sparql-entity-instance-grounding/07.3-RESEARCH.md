# Phase 07.3: NL→SPARQL Entity/Instance Grounding — Research

**Researched:** 2026-07-23
**Domain:** NL→query prompt engineering seam architecture (shared `arango_query_core.nl` engine); RDF instance-label retrieval
**Confidence:** HIGH (architecture/seam boundary, config wiring, eval-harness reuse — all verified by reading the actual shipped code) / MEDIUM (schema-agnostic label-predicate discovery mechanism — reasoned from cross-repo precedent, not yet implemented anywhere) / LOW (production `/nl-execute` live-ArangoDB wiring — genuinely unimplemented, flagged as an explicit gap)

## Summary

This phase does **not** need to re-derive whether grounding works — the spike proved
+12.2pt (McNemar p=0.031, 0 regressions, 96% retrieval recall) and that evidence is
locked. The job is productionization, and the codebase already contains almost every
piece needed to do this cleanly:

1. **The engine has exactly 5 named seams today** (`arango_query_core.nl.seams.QueryLanguageAdapter`:
   grammar, few-shot, validate, repair, guardrails) and grounding is not one of them.
   Entity/instance grounding must become a **6th seam**, added to the shared engine
   package (`arango_query_core`, a separate pinned git dependency, currently at
   `acb60aeeeec2082338a9386d6aa9fd38bb903bdb`), not bolted onto an existing seam.
   The existing `schema_context` parameter on `NLQueryEngine.generate()` is NOT the
   right vehicle — it is documented/used as the *static, cacheable* grammar/schema
   prefix, whereas grounding is inherently *per-question* (like few-shot), so it needs
   its own prompt section analogous to `## Examples`.

2. **The design to mirror is `FewShotIndex`, not Cypher's existing `EntityResolver`.**
   `arango-cypher-py` already ships a mature, adapter-side `EntityResolver`
   (`arango_cypher/nl2cypher/entity_resolution.py`, WP-25.2, ~1100 LOC) — but it is a
   fundamentally different design (per-mention regex extraction + live per-property AQL
   probes with fuzzy/Levenshtein scoring and timeout budgets against a **live ArangoDB**
   handle) that predates this phase and has **not** been re-pointed onto the shared
   `arango_query_core.nl` engine at all (`arango-cypher-py` does not import
   `arango_query_core.nl.engine`/`seams` anywhere — it still runs its own bespoke
   pipeline). This means: (a) there is **zero risk** to Cypher from adding a 6th
   required protocol member to `QueryLanguageAdapter` today (Cypher isn't using the
   protocol), and (b) "so Cypher inherits it" should be read as "design the new engine
   seam generally enough that a *future* Cypher re-point can adopt it," not "migrate
   Cypher's EntityResolver in this phase." The spike's proven design (build one label
   index up front, substring-match top-k per question) is architecturally simpler than
   Cypher's live-probe design and is what actually produced the measured lift — port
   *that*, wrapped as a new engine-side index class following `FewShotIndex`'s exact
   shape (a `Retriever`-like protocol + `format_prompt_section`), not Cypher's resolver.

3. **The eval harness already threads the exact data the grounding index needs.**
   `tests/nl2sparql/eval/runner.py::run()` already loads a corpus-level `data_ttl`
   (CK25's vendored instance graph) once per config run — the same string the spike's
   `build_entity_index()` consumed via `oxi_query`. Wiring a `grounding:` config block
   (mirroring the already-shipped `few_shot:` block exactly) requires **no new
   ArangoDB/db-handle plumbing for the eval proof** — the index can be built once per
   `run()` call from `data_ttl`, exactly like `few_shot_index` is built once outside
   the per-case loop today.

4. **Production `/nl-translate`/`/nl-execute` wiring is a genuine, separate gap.**
   `NlPipeline` currently receives no database handle at all; `/nl-execute` only
   acquires `session.db` *after* `pipeline.run()` returns (to execute the already-
   generated AQL), and `/nl-translate` has no DB access whatsoever. There is today no
   live "target instance data" source to build a production-time label index from.
   This is out of scope for satisfying NL-ACC-01's acceptance criteria (which is
   measured entirely through the eval harness, in-process, never through the FastAPI
   routes) — flagged as an explicit Open Question / follow-on, not a blocker.

**Primary recommendation:** Add a new `arango_query_core/nl/grounding.py` module
(engine-side, generic `LabelIndex`/`GroundedEntity`, ported from the spike's
`build_entity_index`/`retrieve()` almost verbatim), add `grounding_index()` as seam 6
on `QueryLanguageAdapter` + a `grounding_k` engine field, implement `SparqlAdapter`'s
seam over an explicitly-injected index (mirroring the `few_shot_index` injection
pattern exactly), wire a `grounding:` corpus/config key into `runner.py`/`configs.yml`
the same additive way `few_shot:` was wired in Phase 7, and reproduce the spike's
McNemar gate inside the harness using the already-shipped `paired_mcnemar`/
`bootstrap_paired_delta` helpers.

### Pattern 1: Seam 6 — engine-side generic index, adapter-side wording

The five existing seams (`seams.py`) establish the precedent exactly: the engine owns
*flow* (when to call the seam, how to splice its output into the prompt); the adapter
owns everything language-specific. Grounding's retrieval/scoring machinery has zero
SPARQL-specific content (a label string is a label string regardless of target
language) — this is architecturally identical to why `FewShotIndex` lives engine-side
even though `nl2cypher`/`nl2sparql` corpora differ. Follow that precedent for the
*index*, but keep the exact prompt phrasing adapter-side (mirroring how
`grammar_prompt_section` — not `FewShotIndex.format_prompt_section`'s header — owns
target-specific wording).

```python
# Source: verified by reading arango_query_core/nl/seams.py + fewshot.py directly
# (installed at .venv/lib/python3.12/site-packages/arango_query_core/nl/), pattern
# extrapolated from the existing FewShotIndex/QueryLanguageAdapter shape.

# arango_query_core/nl/grounding.py (NEW)
from __future__ import annotations
from dataclasses import dataclass, field
import re

_STOP = frozenset(
    "the a an of in is are on to for me my i give need all every who what "
    "which where when how does do not no and or with by their his her its "
    "please list show find get".split()
)

@dataclass
class GroundedEntity:
    """One retrievable instance: an opaque id + its human-readable labels."""
    id: str
    labels: tuple[str, ...]
    type: str = ""

class LabelIndex:
    """Substring-token retrieval over a fixed list of GroundedEntity records.

    Language-agnostic by construction: `id` is an opaque string (an RDF IRI for
    SPARQL, a node key for Cypher, ...); the retrieval scoring never inspects it.
    Ported from the spike's `retrieve()` (scratchpad/nl-grounding-spike/grounding_spike.py),
    made source-agnostic (the spike queried pyoxigraph directly; here callers build
    `list[GroundedEntity]` however their target data source requires).
    """

    def __init__(self, entities: list[GroundedEntity]) -> None:
        self._entities = entities

    @classmethod
    def from_items(cls, items: list[GroundedEntity]) -> "LabelIndex":
        return cls(items)

    def retrieve(self, question: str, k: int = 20) -> list[GroundedEntity]:
        ql = question.lower()
        q_tokens = {t for t in re.findall(r"[a-z0-9]+", ql) if len(t) >= 3 and t not in _STOP}
        scored: list[tuple[int, int, GroundedEntity]] = []
        for e in self._entities:
            hits = 0
            best_len = 999
            for lab in e.labels:
                labl = lab.lower()
                lab_tokens = [t for t in re.findall(r"[a-z0-9]+", labl) if len(t) >= 3]
                h = sum(1 for t in lab_tokens if t in ql)
                h += sum(1 for t in q_tokens if t in labl and not any(t == lt for lt in lab_tokens))
                if h > hits:
                    hits, best_len = h, len(labl)
            if hits:
                scored.append((hits, -best_len, e))
        scored.sort(key=lambda x: (x[0], x[1]), reverse=True)
        return [e for _, _, e in scored[:k]]

    def format_prompt_section(
        self, question: str, k: int = 20, *, header: str, instruction: str, id_prefix: str = ""
    ) -> str:
        """Generic renderer — header/instruction text is adapter-supplied so the
        exact wording ("EXACT IRIs" vs "exact node IDs") stays language-specific
        while the bullet-list mechanics stay shared."""
        matches = self.retrieve(question, k=k)
        if not matches:
            return ""
        lines = [header, instruction, ""]
        for e in matches:
            lab = " / ".join(sorted(e.labels))
            lines.append(f'- {id_prefix}{e.id} — "{lab}" ({e.type or "?"})')
        return "\n".join(lines)
```

    grounding_k: int = 20

    def _system_prompt(self, question: str, schema_context: str) -> str:
        sections = [self.adapter.grammar_prompt_section(schema_context)]
        index = self.adapter.few_shot_index()
        if index is not None:
            examples = index.format_prompt_section(question, k=self.few_shot_k, language=self.adapter.language)
            if examples:
                sections.append(examples)
        grounding = self.adapter.grounding_index()
        if grounding is not None:
            block = self.adapter.grounding_prompt_section(question, grounding, k=self.grounding_k)
            if block:
                sections.append(block)
        return "\n\n".join(s for s in sections if s)

### Pattern 2: Eval-harness-only pyoxigraph builder (packaging boundary)

```python
# Source: pattern extrapolated from tests/nl2sparql/eval/runner.py::_build_label_map
# (already ships an almost-identical rdfs:label query for judge-side IRI→label
# normalization) and scratchpad/nl-grounding-spike/grounding_spike.py::build_entity_index.
# Lives under tests/ — NEVER inside arango_query_core or arango_sparql (pyoxigraph
# stays a [dev]-only test dependency per CLAUDE.md hard rule 5).

def build_label_index(data_ttl: str, label_predicates: list[str]) -> LabelIndex:
    from tests.helpers.oxi import load_store_from_string, oxi_query
    store = load_store_from_string(data_ttl)
    predicate_union = "|".join(f"<{p}>" for p in label_predicates)
    q = f"""
    SELECT ?s ?label ?type WHERE {{
      ?s ({predicate_union}) ?label .
      OPTIONAL {{ ?s a ?type }}
    }}"""
    by_iri: dict[str, dict] = {}
    for row in (oxi_query(store, q).rows or []):
        iri = row.get("s")
        if not iri:
            continue
        label = (row.get("label") or "").strip('"').split('"^^')[0]
        e = by_iri.setdefault(iri, {"labels": set(), "type": ""})
        if label:
            e["labels"].add(label)
        if row.get("type") and not e["type"]:
            e["type"] = row["type"].rsplit("/", 1)[-1].rstrip(">")
    from arango_query_core.nl.grounding import GroundedEntity, LabelIndex
    return LabelIndex.from_items(
        [GroundedEntity(id=iri.strip("<>"), labels=tuple(v["labels"]), type=v["type"])
         for iri, v in by_iri.items()]
    )
```

### Anti-Patterns to Avoid

- **Reusing `schema_context` for the entity block.** It is documented and used as the
  *static* grammar/schema prefix (see `adapter.py`'s `grammar_prompt_section`: `ttl =
  self.ontology_ttl or schema_context`); grounding is per-question and belongs in its
  own section, not conflated with the cacheable static prefix
  (`split_system_for_anthropic_cache` treats `## Examples` as the cache boundary —
  a new dynamic section must land in the same post-boundary region, not before it).
- **Migrating Cypher's `EntityResolver` into the shared engine this phase.** It is a
  different, live-DB-probe design; forcing it into a `LabelIndex`-shaped seam is a
  much larger, separate, cross-repo undertaking explicitly out of this phase's scope
  ("lever #1 (grounding) ONLY" per ROADMAP). Design the seam so it's *adoptable* by
  Cypher later; do not attempt the adoption now.
- **Hardcoding `pv:name` in engine-side or adapter-side production code.** It is a
  CK25-specific predicate local name; hardcoding it violates the explicit "never
  CK25-specific hand-curation" invariant. Keep it in `configs.yml`'s
  `label_predicates:` list (declarative config, not code) at minimum; see § Common
  Pitfalls for the stronger auto-discovery alternative.
- **Rebuilding the label index per corpus case.** Exactly the same Pitfall 1 already
  called out for `few_shot_index`/`DenseRetriever` in this file's own comments
  (expensive re-embedding/re-querying per case) — build once per `run()` call.
- **Letting a live LLM sweep silently replace the fresh-zero-arm discipline.** Per
  README §7.2's established pitfall: the confirmatory comparison must be
  grounded-vs-a-freshly-run-zero-arm in the *same session*, never grounded-vs-the-
  already-committed `openai-gpt4o-mini-ck25` baseline number (model drift between
  sessions is a real, previously-encountered confound — see 07-04's M2 note).

| Problem | Don't Build | Use Instead | Why |

| Statistical significance test | A new McNemar/bootstrap implementation | `tests/nl2sparql/eval/runner.py::paired_mcnemar`/`bootstrap_paired_delta` (already shipped, pure-Python, no scipy) | Already proven correct against the spike's own numbers; re-deriving risks a subtly different exact-test formulation |

## Common Pitfalls

### Pitfall 1: Conflating grounding wording with the static schema prefix
**What goes wrong:** Appending the entity block inside `grammar_prompt_section`
(or via `schema_context`) breaks the documented cache-boundary contract
(`split_system_for_anthropic_cache` assumes everything before `## Examples` is
question-invariant) and makes the block impossible to omit cleanly when the index
is empty.
**Why it happens:** `schema_context` is sitting right there, unused by
`pipeline.py` (`engine.generate(nl, schema_context="")`), and looks like a
convenient hook.
**How to avoid:** Add the 6th seam as designed above; never touch `schema_context`.
**Warning signs:** A test asserting the entity block appears in
`grammar_prompt_section`'s OWN return value (it should only appear in the engine's
composed `_system_prompt`, exactly as `test_fewshot_engine_prompt.py` already
asserts for the few-shot section — mirror that test file's SC-gate shape).

### Pitfall 2: Hardcoded label-predicate list silently fails to generalize to CDF
**What goes wrong:** Shipping `label_predicates: ["rdfs:label", "pv:name"]` as a
hardcoded DEFAULT (not just CK25's specific config entry) means the very first
non-CK25 deployment (the stated CDF-transfer requirement) gets zero grounding
unless someone remembers to add its own label predicate(s) — silently degrading
to the ungrounded 12% floor with no error.
**Why it happens:** `pv:name` genuinely is CK25-specific; there is no universal
RDF convention for "the name property" beyond `rdfs:label`.
**How to avoid:** Two viable levels of ambition (present both to the planner as
options, pick per available Wave budget):
  - **Minimum viable (config-only):** default `label_predicates` to `["rdfs:label"]`
    globally; CK25's *own* config entry explicitly adds `pv:name`. This satisfies
    "not hand-curated in code" (it's declarative config, reviewable, and any future
    deployment adds its own line) without new engineering.
  - **Stronger (auto-discovery):** derive extra label predicates from the
    already-available `ontology_ttl`/`resolver` by scanning `owl:DatatypeProperty`
    declarations whose **local name** (case-insensitive) is in a small generic set
    (`name`, `label`, `title`, `identifier`) — this is empirically verified to work
    for CK25 (`pv:name`'s own `rdfs:label "name"@en` confirms the local name is
    literally `name`) and closely mirrors Cypher's already-battle-tested
    `_STRING_PROPERTY_CANDIDATES`/role-priority heuristic
    (`arango_cypher/nl2cypher/entity_resolution.py`), giving genuine cross-repo
    consistency for "what counts as a nameable field" without hardcoding a single
    dataset's vocabulary.
**Warning signs:** A CDF-domain smoke test (if one exists/gets added) showing 0
retrieved entities for every question despite instance data being present.

### Pitfall 3: Building the index inside the per-case loop
**What goes wrong:** Re-parsing the Turtle / re-running the enumeration SPARQL
query on every one of 49 cases — 49x the work for identical output, and (if a
future production wiring adds a dense/embedding-scored variant) 49x model
inference cost, exactly the already-documented Pitfall 1 for `few_shot_index`/
`DenseRetriever`.
**Why it happens:** The natural, naive place to construct a per-request object is
inside `NlPipeline.__init__` or inside the loop that constructs per-case pipelines.
**How to avoid:** Build once, outside the loop, in `runner.py::run()` — exactly
where `few_shot_index` is already built once today. Pass the SAME object into
every case's `NlPipeline(...)`.
**Warning signs:** Wall-clock time scaling linearly with corpus size well beyond
LLM-call latency; a profiler showing repeated `oxi_query`/Turtle-parse calls.

### Pitfall 4: Git-pin remote mismatch when bumping `arango-query-core`
**What goes wrong:** `pyproject.toml` pins
`git+https://github.com/ArthurKeen/arango-query-core@<sha>`, while `uv.lock`
resolves via `github.com/arango-solutions/arango-query-core.git?rev=<sha>`, and the
local dev checkout's `git remote -v` shows `origin` → `arango-solutions/...`.
Both remotes currently resolve to the identical commit (`acb60ae...`, verified via
`git ls-remote` against both URLs this session), so they are in sync today — but a
push to the wrong one (or a future divergence) would silently leave the pin
unfetchable or pointing at stale content.
**Why it happens:** Two GitHub identities/orgs host what is effectively the same
repo (fork/mirror relationship not otherwise documented in this session).
**How to avoid:** After making + committing the engine-side change locally, verify
BOTH remotes reflect the new commit via `git ls-remote` before updating
`arango-sparql-py`'s pin (exactly the verification STATE.md records for 07-03's
"M5 origin-fetchability verified live via git ls-remote before uv lock").
**Warning signs:** `uv lock` succeeding against a stale commit because one remote
lagged behind the other.

### Pitfall 5: Confusing the "scripted" gate with a model-accuracy measurement
**What goes wrong:** Treating `scripted-ck25-grounded`'s pass rate as evidence
grounding works. `scripted` configs replay a canned response
(`ScriptedLLMClient`) — they test that the *plumbing* (config → index → seam →
prompt → judge) doesn't crash and that CI stays green, not that grounding changes
model behavior.
**Why it happens:** It's tempting to treat any green pytest run as "proof."
**How to avoid:** The only evidence that counts for NL-ACC-01 is the live,
credentialed, human-run `openai-gpt4o-mini-ck25-grounded` vs. a freshly-run
`openai-gpt4o-mini-ck25` zero arm, compared via `paired_mcnemar` — exactly the
already-established README §7 discipline.
**Warning signs:** A plan/summary citing `scripted-ck25-grounded: pass_rate=X` as
if it were the accuracy proof.
