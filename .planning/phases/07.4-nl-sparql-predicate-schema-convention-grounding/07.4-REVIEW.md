## Critical Issues

### CR-01: "Dump mode" never actually dumps the schema — `effective_k` widening is a no-op against the shared retriever's zero-hit filter

**File:** `arango_sparql/nl2sparql/engine_adapter.py:298-324` (mirrored byte-for-byte in `arango_sparql/nl2sparql/adapter.py:149-168`); also misdocumented in `tests/nl2sparql/eval/README.md:730-737`

**Issue:** Both adapters compute, for a schema at or under `PREDICATE_DUMP_THRESHOLD` (40):

```python
total = len(getattr(index, "_predicates", ()))
effective_k = total if 0 < total <= PREDICATE_DUMP_THRESHOLD else k
return index.format_prompt_section(question, k=effective_k, ...)
```

The comment above this line (both files) and `README.md:730-731` both assert
this achieves "dump mode": *"CK25's 30 predicates dump in full"*. It does
not. `PredicateIndex.format_prompt_section` (the pinned `arango_query_core`
dependency, `arango_query_core/nl/grounding.py`) unconditionally delegates to
`self.retrieve(question, k=k)`, and `retrieve`'s shared scorer
(`_token_substring_retrieve`) drops every candidate with zero label/domain/
range token overlap against the question **regardless of `k`**:

```python
if hits:
    scored.append((hits, -best_len, item))
...
return [item for _, _, item in scored[:k]]
```

`k` only caps the candidate list *after* the zero-hit filter — it can never
add back predicates the question didn't lexically touch. Widening
`k` from 20 to `total` (30 for CK25) therefore has **no effect** whenever the
number of question-matching predicates is already below 20, which is true
for essentially every CK25 question. Verified directly against the real
vendored CK25 TBox:

```
total predicates: 30
ck25-1 -> retrieved 4 of 30  ("In which department is Ms. Brant?")
ck25-2 -> retrieved 1 of 30  ("What is the telephone of Baldwin Dirksen?")
ck25-5 -> retrieved 7 of 30  ("Who has expertise in Transistors?")
ck25-7 -> retrieved 8 of 30  ("Who is the manager of the Data Services department?")
```

So for a typical question, the model sees 1-8 of CK25's 30 predicates — not
"the full schema" as designed and documented. This directly contradicts the
phase's own threat-model claim (`07.4-RESEARCH.md`'s DoS mitigation row:
*"any schema over the threshold is retrieval-limited to `k` predicates per
call, never dumped in full"* — implying schemas **under** the threshold ARE
meant to be dumped in full, unconditionally) and invalidates the premise
under which the D-01 design was pitched (the model needs to see every
convention-bound predicate, including ones the question doesn't name, to
learn the value-object/category-instance hop shapes).

This is very likely the root cause of the NL-ACC-02 null/regression result
already folded into `baseline.json` (`configs.openai-gpt4o-mini-ck25-predicate-grounded`
and `phase07_4_predicate_grounding_sweep.ck25_additive_arm`): the
predicate-grounded arm never actually delivered "the full 30-predicate
schema" to the model as the design intended — it delivered a relevance-
filtered subset barely larger than the QALD retrieve-mode arm's `k=20`. The
recorded "seam-7 gives no lift" conclusion is confounded by this
implementation defect and should not be treated as a clean test of the D-01
hypothesis.

**Fix:** Implement a real dump path that bypasses the shared retriever's
substring filter entirely when `0 < total <= PREDICATE_DUMP_THRESHOLD`,
e.g.:

```python
if 0 < total <= PREDICATE_DUMP_THRESHOLD:
    # Genuine dump: every predicate, unconditionally — retrieve()'s
    # hits>0 filter makes widening k alone insufficient (see CR-01).
    return _render_all_predicates(index._predicates, header=..., instruction=...)
return index.format_prompt_section(question, k=k, header=..., instruction=...)
```

Since `PredicateIndex.format_prompt_section`'s only entry point is
`retrieve()`, this requires either (a) a small upstream addition to
`arango_query_core.nl.grounding.PredicateIndex` (e.g. an `all()`/`dump=True`
render path, reusing its existing `_sanitize_label` + two-tier rendering),
or (b) a local re-implementation of the two-tier render loop in this repo's
adapter files for the dump branch. Either way, the NL-ACC-02 CK25
predicate-grounded sweep (`baseline.json`) should be re-run once real dump
mode ships, and the current "documented null" disposition should be
annotated as provisional/confounded until then.

## Warnings

### WR-01: `build_predicate_index()` silently collapses multi-valued `rdfs:domain`/`rdfs:range`/`rdfs:label` to one arbitrary value

**File:** `tests/nl2sparql/eval/grounding_index_builder.py:263-275` (Pass 1 aggregation) and `:293-302` (Pass 2 aggregation)

**Issue:** SPARQL's `OPTIONAL` produces one result row per matched
combination, so if a predicate declares more than one `rdfs:domain`,
`rdfs:range`, or `rdfs:label` triple, `pass1_query` returns multiple rows for
that predicate IRI. `declared[iri] = {...}` (plain dict assignment) silently
overwrites on every row, so only the last-seen combination survives —
non-deterministically, since row order depends on the store's internal
iteration order, not any declared precedence. Reproduced directly:

```python
# ex:hasThing declares BOTH rdfs:domain ex:Widget AND rdfs:domain ex:Gadget
idx = build_predicate_index(ttl)
# -> only ONE GroundedPredicate is emitted, domain="Widget" (the other silently dropped)
```

The same overwrite-on-duplicate pattern applies to Pass 2's `children`
list (duplicate `(label, range)` entries would silently appear in
`shape_detail` for a multi-valued child, and a multi-domain child could be
miscounted for the all-datatype-children shape check). Neither CK25 nor the
QALD DBpedia subset currently declares multi-valued domain/range/label
(verified directly against both vendored TBoxes — zero occurrences today),
so this doesn't affect the current corpora, but it is exactly the kind of
mechanical, no-hand-curation code this phase explicitly designed to
"generalize to CDF" (per the module docstring), and a future schema with
multi-valued declarations would silently and non-deterministically corrupt
the rendered predicate block with no warning, log, or test failure.

**Fix:** Either explicitly dedupe/aggregate multi-valued declarations
(e.g. collect into a sorted tuple and pick a deterministic first value,
logging a warning), or add a load-time assertion that fails loudly if a
predicate declares more than one `rdfs:domain`/`rdfs:range`/`rdfs:label`
(mirroring this codebase's existing "fail loud on ambiguous input" pattern
used elsewhere, e.g. `CorpusCase._gold_must_parse` in `runner.py`), so a
future corpus with this shape surfaces as a test failure rather than a
silent, non-deterministic misclassification.

### WR-02: Unvalidated string interpolation of TBox-derived IRIs into SPARQL query text

**File:** `tests/nl2sparql/eval/grounding_index_builder.py:283-292`

**Issue:** Pass 2's per-class query interpolates `class_iri` (an IRI string
extracted from the ontology being walked) directly into a SPARQL query via
an f-string: `rdfs:domain <{class_iri}> .`. While well-formed IRIs cannot
legally contain a bare `>`, this value is not validated before
interpolation, and the same pattern already exists in `build_label_index`'s
`predicate_union` construction (pre-existing, not introduced by this diff).
For the currently trusted, checked-in corpus TBoxes this is low risk, but
this eval harness is explicitly aimed at generalizing to future
externally-sourced schemas (CDF, per the module docstring); an
adversarially- or accidentally-malformed TBox literal containing `>` inside
what's nominally an IRI position could alter the query's structure. Not
exploitable today (no untrusted input reaches this path), but worth
hardening before this builder is pointed at any TBox that isn't fully
repo-controlled.

**Fix:** Validate/escape `class_iri` before interpolation (e.g. reject or
percent-encode any `>`/`{`/`}` before building the query string), or use a
parameterized query construction if pyoxigraph's SPARQL API supports it.

## Info

### IN-01: Cross-adapter parity test doesn't exercise the retrieve-mode branch

**File:** `tests/nl2sparql/test_grounding_prompt_parity.py:85-99`

**Issue:** `test_predicate_prompt_section_byte_identical_across_adapters`
only builds a 1-predicate `PredicateIndex` (`total=1`, always `<=
PREDICATE_DUMP_THRESHOLD`, so `effective_k` trivially equals `total` in both
branches of the `if`). It never exercises the `else k` branch (a schema
above the threshold), so a future edit that diverges the two adapters'
retrieve-mode `k` handling (as opposed to dump-mode) would not be caught by
this parity gate.

**Fix:** Add a second fixture with `>40` predicates to exercise the
`else k` branch in the parity assertion.

### IN-02: `write_report()` now persists generated SPARQL per case

**File:** `tests/nl2sparql/eval/runner.py:741-744`

**Issue:** The JSON payload written by `write_report()` now includes
`"sparql": c.actual` per case (previously only `name`/`passed`/`elapsed_ms`).
`reports/` is gitignored, so this doesn't violate the README's "never
commit raw prompts/completions" discipline, but it is a scope change to a
function multiple `README.md` sections describe by an older, narrower shape
— worth a one-line README update so the documented schema doesn't drift
from the actual JSON shape.

**Fix:** Update `README.md`'s Pitfall 2 callout (`write_report()`'s flat
shape) to mention the new `sparql` field, or omit it if it wasn't an
intentional addition.
