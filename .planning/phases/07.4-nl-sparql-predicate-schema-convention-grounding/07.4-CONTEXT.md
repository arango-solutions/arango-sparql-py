# Phase 07.4: NL→SPARQL predicate/schema-convention grounding - Context

**Gathered:** 2026-07-24
**Status:** Ready for planning

<domain>
## Phase Boundary

Extend the grounding seam (seam 6, shipped in Phase 07.3 for *instance entities*)
to **predicates and schema conventions**. Walk the OWL/RDFS TBox to surface each
schema predicate with its label, domain, range, object-vs-datatype nature, and a
**mechanically-derived usage shape**, and inject that into the LLM prompt so the
model binds to real predicates in their real shape — instead of inventing
nonexistent classes (`?x a :Oscillator`) or flattening structured values
(`?x :price ?p` where price is actually a value object).

**Motivating evidence (this session's CK25 error analysis).** After entity
grounding (07.3): 14/49 pass, +9 gained, **0 regressions**, **35 still failing**.
Of the 35: **17 are convention-bound** (low structural complexity, fail on schema
conventions — the population predicate grounding can plausibly fix), 13 mixed
(predicate + structure), 5 structure/compute-dominated. Two systematic patterns
dominate the convention-bound bucket and are **mechanically derivable from the
CK25 TBox** (verified): the **price value-object** (`?x pv:price ?p . ?p pv:amount ?a`,
~8 cases; `pv:price` range `pv:Price`, `pv:amount`/`pv:currency` domain `pv:Price`)
and the **`hasCategory` product-typing convention** (`?x pv:hasCategory <…prod-cat-X>`,
~9 cases; `pv:hasCategory` range `pv:ProductCategory`).

**In scope:** predicate/schema-convention grounding as an extension of seam 6;
eval-only predicate-index builder (TBox walk); CK25 acceptance gate; QALD
directional generalization check; generated-SPARQL capture in eval reports.

**Out of scope:** structural/compositional failures (superlatives → ORDER BY/LIMIT,
aggregation, percentiles, cycle detection) — a *later* lever (few-shot pattern
coverage or query decomposition); fine-tuning; changing the transpiler.

</domain>

<decisions>
## Implementation Decisions

### Injection scope (glossary size)
- **D-01:** **Retrieve + auto-dump-when-small.** Build a "retrieve the predicates
  relevant to this question" path (reuse the engine's existing few-shot / entity
  retrieval machinery where possible), but when the schema is below a size
  threshold (CK25's ~30 predicates) dump the **whole** predicate set. A size check
  picks the mode per call. Rationale: the lever must transfer to a large CDF /
  DBpedia-scale schema (retrieve), while staying lossless on small schemas (dump).
  This is a required generalization property, not an optimization.

### Predicate shape / convention encoding
- **D-02:** **Derive usage shape mechanically from the TBox.** For each predicate
  inject label + domain + range + object-vs-datatype, and render the convention
  from those declarations (e.g. "`price` → a Price object with `amount` + `currency`";
  "`hasCategory` → points to a ProductCategory instance"). **No hand-authored,
  per-schema hints** — honors the 07.3 "no CK25-specific hand-curation so it
  transfers to CDF" principle (see NL-ACC-01). The two dominant failure patterns
  are fully declared in the CK25 TBox, so this is a mechanical schema walk, not
  curation.

### Measurement scope + cost
- **D-03:** **CK25 = hard gate; QALD = directional generalization check.** Hard
  acceptance: same-session CK25 **predicate-grounded vs the 07.3 entity-grounded
  baseline** (`baseline.json:openai-gpt4o-mini-ck25-grounded` = 14/49), McNemar
  **p<0.05, 0 regressions**. Additionally: the **first-ever live run of the powered
  QALD-9-plus gate** (514 cases, never run against a live model) — zero-shot +
  predicate-grounded — as a directional signal that the lever generalizes beyond
  the 49-case corporate anchor. QALD is NOT a hard gate this phase (avoid
  over-scoping), but predicate grounding on DBpedia's large schema is exactly the
  "retrieve" path from D-01, so it's the natural place to prove scaling. Cost:
  gpt-4o-mini, a few dollars total.
- **D-04:** Honest ceiling recorded so the phase isn't over-promised: predicate
  grounding plausibly converts the **17 convention-bound** cases and contributes
  to the 13 mixed; realistic CK25 target ~14 → ~20–25, **not** all 35. The
  structural residual is explicitly deferred (see Deferred Ideas).

### Eval instrumentation
- **D-05:** **Capture generated SPARQL per case** in eval reports (eval tier only,
  never CI-default, no secrets). Turns the entity-vs-predicate failure attribution
  from a demand-analysis proxy into confirmed fact, and makes all future NL→SPARQL
  error analysis free. Reports currently store only `{name, passed, elapsed_ms}`.

### Carried forward from Phase 07.3 (locked — do not re-litigate)
- **D-06:** Grounding is a **language-agnostic seam in shared `arango_query_core`**;
  the Cypher sister repo inherits it. Predicate grounding must be a generic engine
  member, not a SPARQL-only hack.
- **D-07:** The grounding block is **engine-composed into the system prompt, after
  few-shot**, and MUST NOT leak into the cacheable `grammar_prompt_section` (SC-gate
  `test_grounding_engine_prompt.py` enforces this cache boundary; extend it for the
  predicate block).
- **D-08:** Eval-only pyoxigraph/TBox builder stays **confined to `tests/`** with a
  function-local pyoxigraph import; scripted configs stay the sole CI-reachable
  default; W3C DAWG coverage ≥96.4%; SPARQL→AQL transpiler package untouched.
- **D-09:** New requirement **NL-ACC-02** (predicate/schema-convention grounding
  lift), modeled on NL-ACC-01's acceptance shape.

### Claude's Discretion
- Whether predicate grounding is a new seam member vs. an extension of the existing
  `grounding_index()`/`grounding_prompt_section()` signatures; whether the injected
  predicate block and entity block share one "## Known schema/entities" section or
  are separate — planner/researcher decide, subject to D-07's cache boundary and
  cross-adapter parity (`test_grounding_prompt_parity.py`).
- The exact dump-vs-retrieve size threshold and the predicate-retrieval mechanism
  (reuse few-shot retriever vs. a dedicated predicate index) — research question.
- Compact rendering format of the shape hint (research: minimize tokens while
  conveying the value-object / category-instance structure).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`LabelIndex`/`GroundedEntity` + generic renderer** (`arango_query_core/nl/grounding.py`): the exact structural analog for a predicate index — a `PredicateIndex`/`GroundedPredicate` can mirror it.
- **Seam 6 (`grounding_index`/`grounding_prompt_section`)**: the injection point already exists and is wired end-to-end (engine → adapter → pipeline). Predicate grounding extends this rather than adding new plumbing.
- **`build_label_index()`** (`grounding_index_builder.py`): already walks the graph with a function-local pyoxigraph import and excludes schema/structural terms (CR-01) — the inverse walk (extract the TBox predicates + domain/range) reuses the same machinery and the same confinement discipline.
- **Few-shot retriever** (engine): candidate reuse for the "retrieve predicates by question" path (D-01) — research whether it generalizes or needs a dedicated predicate index.
- **Power module** (`power.py`): reuse for MDE reporting on the QALD directional run.

### Established Patterns
- **Engine-composed prompt, after few-shot, out of the cacheable grammar section** (SC-gate). The predicate block obeys the same cache boundary (D-07).
- **Additive, default-preserving config** in `runner.py`/`configs.yml`; every pre-existing config stays byte-identical.
- **Deterministic recall guard in the always-on CI tier** (no `RUN_EVAL`); live sweeps human-run and credentials-gated; scripted-only in CI.
- **Separate per-corpus baseline entries, never blended.**

### Integration Points
- New `configs.yml` entries: `scripted-ck25-predicate-grounded` (plumbing gate), `openai-gpt4o-mini-ck25-predicate-grounded` (live gate arm), and QALD `{scripted,openai-gpt4o-mini}-qald9plus-predicate-grounded` for the directional check + the first live `openai-gpt4o-mini-qald9plus` zero-shot arm.
- `runner.py`: build predicate index once before the per-case loop (mirror the label-index build-once); add generated-SPARQL capture to the report writer (D-05).

</code_context>

<specifics>
## Specific Ideas

- The value-object and category conventions are the concrete acceptance targets — a passing phase should visibly convert cases like `ck25-9` ("How many Sensor Switches?" → `hasCategory` to two category IRIs) and `ck25-19` ("most expensive service" → `price`→`amount` value-object hop).
- Keep the QALD run framed as "first powered number + generalization signal," not a gate — it also finally lights up the 514-case gate that 07.1 built but never ran live.

</specifics>

<deferred>
## Deferred Ideas

- **Structural/compositional lever** — the ~13 mixed + 5 structure-dominated CK25 failures (superlatives → ORDER BY/LIMIT, aggregation/GROUP BY, computed quantities like density/volume, percentiles, compatibility cycles) that predicate grounding will NOT fix. Future phase: few-shot pattern coverage and/or query decomposition. (D-04)
- **Generator fine-tuning** — the user's originally-selected lever; deferred to v1.1 with the transfer caveat (QALD-trained weights bake in DBpedia specifics and likely won't transfer to CDF; if pursued, train on target-domain synthetic data, not QALD, and keep few-shot+grounding on in both arms).
- **Modern embedder / hybrid retrieval** — cheap hedge that would lift BOTH few-shot and grounding retrieval recall; do it *with* the D-01 retrieval work if retrieval recall proves to be the ceiling, not standalone.
- **QALD as a co-equal powered hard gate** — considered and deferred to keep this phase focused (D-03).
