## Summary

This phase extends the seam-6 grounding pattern shipped in Phase 07.3 (instance/entity
IRI grounding) to the TBox itself: predicates and the structural conventions their
domain/range declarations imply. The central, verified finding of this research is that
**the raw domain/range triples the model needs are already present in every corpus's
prompt** — `PromptBuilder.render_system()` embeds the full `ontology:` Turtle block
(`corpus["ontology"]`, confirmed to include `pv:price rdfs:range pv:Price`,
`pv:amount rdfs:domain pv:Price`, `pv:hasCategory rdfs:range pv:ProductCategory` verbatim)
into the grammar prompt on every call, for every config, today. Zero-shot and
entity-grounded runs both already see these declarations. The 17 convention-bound
CK25 failures are therefore not an information-availability gap — they are an
**operationalization gap**: an LLM reliably reads "`?x pv:price ?p`" out of a
zero-shot free-text question far more readily than it reliably infers "...and
`?p` is not a literal, it's a `Price` object, so hop again for `?p pv:amount`" from
raw declarative OWL triples buried in a 16KB ontology block. The lever this phase
adds is not *new information* but a **distilled, imperative, per-predicate usage
cheat-sheet** that restates the same facts in a form an LLM reliably executes on.

The second major finding structurally simplifies this phase relative to 07.3:
**no new corpus-level file is needed.** Entity grounding required vendoring a new
`data_path:` instance graph per corpus. Predicate grounding's mechanical TBox walk
can run entirely against `corpus["ontology"]` (`shared_ontology` in `runner.py`),
which **every** corpus already has — CK25 (30 properties) and QALD-9-plus (250
properties, confirmed via `grep -c owl:ObjectProperty|owl:DatatypeProperty`) both
qualify, with no vendoring work. This also resolves D-01's generalization
requirement concretely: CK25's 30 predicates sit comfortably under a dump-all
threshold while QALD's 250 sit ~6x over it, giving a real (not synthetic) test of
both code paths in this repo's own existing fixtures.

The third finding: the mechanical shape-derivation rule needs one refinement
beyond the CONTEXT.md sketch to avoid a real false positive discovered by testing
it against the actual TBox (`pv:hasManager` → range `pv:Manager`, and `pv:Manager`
does have a property with domain=`pv:Manager` — `pv:hasDirectReport` — which a
naive "range class has ≥1 own property" rule would mis-flag as a "value object"
shape identical to `Price`). The corrected 3-way rule (below) only flags "value
object" when the range class's own properties are exclusively *datatype*
properties; it correctly separates `Price` (value object) and `ProductCategory`
(bare category instance) from `Manager`/`Supplier`/`Employee`/`Department`
(ordinary linked entities, already covered by entity grounding, not predicate
grounding).

**Primary recommendation:** Add a new seam 7 (`predicate_index()` /
`predicate_prompt_section()`) to `arango_query_core.nl.seams.QueryLanguageAdapter`,
structurally mirroring seam 6 exactly (new `GroundedPredicate`/`PredicateIndex`
classes in `grounding.py`, reusing — via a small extraction — `LabelIndex`'s
token-substring retrieval algorithm). Build the predicate index once per eval run
from `corpus["ontology"]` via a function-local-pyoxigraph TBox walk
(`build_predicate_index()`, sibling to `build_label_index()` in
`grounding_index_builder.py`), applying the corrected 3-way shape rule. Render a
compact, two-tier prompt block (terse domain→range→kind line for every listed
predicate; an expanded imperative shape-hint + example triple pattern only for
value-object/category-instance predicates). Compose it in the engine immediately
after the existing entity block, so ordering becomes grammar → few-shot → entities
→ predicates, all post-cache-boundary. Implement seam 7 on **both** adapters
(`engine_adapter.SparqlAdapter` and legacy `adapter.SparqlLanguageAdapter`) in the
**same** commit that bumps the `arango-query-core` pin — 07.3-02 already proved
what happens when this is done non-atomically (3 test failures in the legacy
adapter, fixed a plan later in 07.3-03). D-05's query-capture requirement is
already ~90% done: `CaseResult.actual` already stores the generated SPARQL; the
only gap is that `write_report()`'s JSON payload dict-literal omits it — a
one-line fix, not new plumbing.

### Pattern 1: Mechanical shape derivation (D-02), corrected 3-way rule

**What:** For every `owl:ObjectProperty`/`owl:DatatypeProperty` P declared in the
TBox, classify its rendering shape purely from rdfs:domain/rdfs:range
declarations — no per-schema hand curation.

**Rule (verified against the real CK25 TBox,
`tests/nl2sparql/eval/vendored/ck25/raw/prod-inst-schema.ttl`):**

1. `kind = "datatype"` if `P a owl:DatatypeProperty` → `shape = "literal"`.
   Render: domain, range (XSD local name), nothing else.
2. `kind = "object"` if `P a owl:ObjectProperty`, with `range = C` (a class).
   Let `children(C)` = properties with an *explicitly declared*
   `rdfs:domain == C` (exact match only — do **not** walk `rdfs:subClassOf`
   inheritance; this is what avoids over-firing, see below).
   - If `children(C)` is non-empty **and every member of `children(C)` is a
     DatatypeProperty** → `shape = "value_object"`. Shape detail = the
     `(label, range)` pairs of those datatype children.
   - If `children(C)` is **empty** → `shape = "category_instance"` (P points
     to a bare named individual with no further declared structure of its
     own; defer to entity grounding — seam 6 — for the exact IRI).
   - Otherwise (`children(C)` is non-empty but contains at least one
     ObjectProperty) → `shape = "linked_entity"` — an ordinary object link;
     no special hint needed (already covered by entity grounding, and the
     raw ontology block already states domain/range unambiguously for
     plain 1-hop object links).

**Why the exact-domain-match / all-datatype-children refinement is necessary**
(discovered empirically, not assumed): `pv:hasManager` has range `pv:Manager`.
`pv:Manager` **does** have a property with domain `pv:Manager` —
`pv:hasDirectReport` (an `owl:ObjectProperty`, range `pv:Employee`). A naive
"range class has ≥1 own property" rule (the literal CONTEXT.md phrasing) would
misclassify `pv:hasManager` as a `"value_object"` shape identical to `pv:price`,
which is wrong — `Manager` is a normal entity class, not a value object, and
prompting the model to expect a value-object hop there would be actively
misleading. The corrected rule (all-children-must-be-datatype) separates this
case correctly: `pv:price`→`pv:Price` has children `{pv:amount, pv:currency}`,
both DatatypeProperty → `value_object`. `pv:hasManager`→`pv:Manager` has
children `{pv:hasDirectReport}`, an ObjectProperty → `linked_entity` (correct,
no false positive). `pv:hasCategory`→`pv:ProductCategory` has zero children →
`category_instance` (correct, matches the CONTEXT.md target exactly).
Cross-checked against every other object property in the TBox (`hasSupplier`→
`Supplier`, `memberOf`→`Department`, `hasProductManager`→`Employee`,
`eligibleFor`→`Product`, `compatibleProduct`→`Product`, `hasBomPart`→`BomPart`,
`hasPart`→`Product`, `areaOfExpertise`→`ProductCategory`, `country`→`dbo:Country`,
`responsibleFor`→`Product`) — none produce a false `value_object` under the
corrected rule; only `price` does, matching the CONTEXT.md-documented target
exactly.

### Pattern 2: TBox walk query (two-pass, pyoxigraph, function-local import)

```sparql
-- Source: proposed, modeled on grounding_index_builder.py::build_label_index's
-- existing query-construction style (same file, sibling function)
PREFIX owl: <http://www.w3.org/2002/07/owl#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

-- Pass 1: every declared property + its own label/domain/range
SELECT ?p ?kind ?label ?domain ?range WHERE {
  { ?p a owl:ObjectProperty . BIND("object" AS ?kind) }
  UNION
  { ?p a owl:DatatypeProperty . BIND("datatype" AS ?kind) }
  OPTIONAL { ?p rdfs:label ?label }
  OPTIONAL { ?p rdfs:domain ?domain }
  OPTIONAL { ?p rdfs:range ?range }
}
```

```sparql
-- Pass 2: run once per distinct object-property range class C (cheap — at
-- most ~len(classes) calls against an in-memory store; CK25 has 14 classes,
-- QALD's pruned subset has 75 — both trivial):
SELECT ?childP ?childKind ?childLabel ?childRange WHERE {
  { ?childP a owl:ObjectProperty ; rdfs:domain <C> . BIND("object" AS ?childKind) }
  UNION
  { ?childP a owl:DatatypeProperty ; rdfs:domain <C> . BIND("datatype" AS ?childKind) }
  OPTIONAL { ?childP rdfs:label ?childLabel }
  OPTIONAL { ?childP rdfs:range ?childRange }
}
```

A single combined query with nested `GROUP_CONCAT` is possible but not
recommended: at this data scale (30–250 predicates, an in-memory pyoxigraph
store) the two-pass approach is simpler to write, test, and debug, and mirrors
`build_label_index`'s existing "one clear query, function-local import" style
rather than introducing a more complex aggregate query as the first thing this
phase does.

### Pattern 3: `GroundedPredicate` / `PredicateIndex` (engine-side, sibling repo)

```python
# Source: proposed — mirrors arango_query_core/nl/grounding.py's existing
# GroundedEntity/LabelIndex shape exactly (same file recommended).

@dataclass(frozen=True)
class GroundedPredicate:
    iri: str
    label: str
    kind: str          # "object" | "datatype"
    domain: str         # local name, "" if undeclared
    range: str           # local name (class) or XSD local name
    shape: str           # "value_object" | "category_instance" | "linked_entity" | "literal"
    shape_detail: tuple[tuple[str, str], ...] = ()  # (child_label, child_range) pairs, value_object only


class PredicateIndex:
    """Mirrors LabelIndex exactly; reuses the extracted token-substring scorer."""

    def __init__(self, predicates: list[GroundedPredicate]) -> None:
        self._predicates = list(predicates)

    def retrieve(self, question: str, k: int) -> list[GroundedPredicate]:
        # k >= len(self._predicates) is the "dump" mode (all match trivially,
        # since k caps rather than filters when the candidate count is already
        # <= k); k < len(self._predicates) is the "retrieve" mode. The MODE
        # DECISION (which k to pass) is the adapter's/caller's job, not this
        # class's — mirrors LabelIndex's "no business logic" ethos.
        ...  # calls the shared _token_substring_retrieve(items, get_labels, question, k)

    def format_prompt_section(self, question: str, k: int, *, header: str, instruction: str) -> str:
        ...  # SPARQL-agnostic two-tier renderer stub; adapter supplies header/instruction wording
```

### Pattern 4: Dump-vs-retrieve mode selection (D-01)

**Proposed threshold: 40 total predicates.** CK25 has 30 (dumps in full,
comfortable headroom); QALD-9-plus's authored subset has 250 (retrieves, ~6x
over threshold) — both real fixtures already in this repo, giving a genuine
test of both code paths rather than a synthetic one. `[ASSUMED]` — 40 is a
reasoned default bracketing the two known corpora, not empirically tuned; the
planner should treat it as a named constant (e.g.
`PREDICATE_DUMP_THRESHOLD = 40`) easy to revisit, not a magic number buried in
logic.

```python
# Proposed policy, adapter- or runner-level (not inside PredicateIndex):
effective_k = len(all_predicates) if len(all_predicates) <= PREDICATE_DUMP_THRESHOLD else predicate_k
block = index.format_prompt_section(question, k=effective_k, ...)
```

### Pattern 5: Compact two-tier rendering (research question 3)

```
## Known schema predicates (bind to these EXACT predicates in this EXACT shape)
Use only the predicates listed below, with the exact direction and shape shown.
Predicates marked VALUE OBJECT or CATEGORY require an extra hop — do not flatten
them into a single triple or invent a class not listed here.

- pv:price (Product → Price) [VALUE OBJECT]: `?x pv:price ?p . ?p pv:amount ?amt . ?p pv:currency ?cur`
- pv:hasCategory (Product → ProductCategory) [CATEGORY]: bind directly, e.g. `?x pv:hasCategory <IRI>` — see Known entities for exact IRIs
- pv:hasManager (Employee → Manager)
- pv:hasSupplier (Product → Supplier)
- pv:name (→ xsd:string)
- pv:quantity (BomPart → xsd:decimal)
  ...
```

Only `value_object`/`category_instance`-shaped predicates get the bracketed tag
+ example triple (the two patterns demonstrably driving the 17 convention-bound
failures); `linked_entity`/`literal` predicates get a bare one-line domain→range
summary, since those are already unambiguous 1-hop edges the raw ontology block
already states — the extra annotation would cost tokens without addressing a
demonstrated failure mode. This directly answers the "minimize tokens" research
question: breadth (D-01's dump/retrieve) and per-item verbosity (this pattern)
are two independent knobs, not one.

### Anti-Patterns to Avoid

- **Repeating the raw OWL domain/range triples verbatim as the "predicate
  block."** This is already present in every prompt via the embedded ontology
  block (verified above) and demonstrably insufficient on its own — the value
  add is the *imperative, distilled* restatement, not a second copy of the same
  facts.
- **Walking `rdfs:subClassOf` inheritance when computing `children(C)`.** Doing
  so would re-introduce the false-positive risk this research found and fixed
  (e.g. `pv:Employee`'s inherited `pv:email`/`pv:phone`/`pv:address*` — all
  declared with `rdfs:domain pv:Agent`, not `pv:Employee` — would wrongly
  qualify `Employee`-ranged properties as value-objects under a
  subclass-inclusive walk). Use exact-domain-match only.
- **Hand-listing "price" and "hasCategory" as special-cased strings anywhere in
  code.** D-02 explicitly forbids this; the mechanical rule above must be the
  only source of the shape classification, or the phase does not transfer to
  CDF and violates the locked decision.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Token-substring retrieval scoring for predicates | A second bespoke scorer inside a new `PredicateIndex` | Extract `LabelIndex`'s existing scorer into a shared private helper and call it from both classes | Avoids duplicating ~20 lines of proven, tested ranking logic; guarantees behavioral parity between entity and predicate retrieval for free |
| McNemar / bootstrap CI statistics for the CK25 confirmatory test | A new stats module or a scipy dependency | `runner.py::paired_mcnemar`/`bootstrap_paired_delta` (already implemented, pure-Python, used successfully for NL-ACC-01) | Already proven correct and reused across three prior phases (07, 07.1, 07.3); zero new code |

## Common Pitfalls

### Pitfall 1: Adding a required Protocol member breaks every adapter that doesn't implement it yet (recurrence risk — already hit once)

**What goes wrong:** `QueryLanguageAdapter` is a `runtime_checkable` `Protocol`
with seam methods as plain (non-optional) members. When 07.3-02 bumped the
`arango-query-core` pin to the commit that made seam 6 mandatory, it broke the
**legacy** `SparqlLanguageAdapter` (3 pre-existing `test_adapter.py` failures,
per `STATE.md`'s `[Phase 07.3-02]`/`[Phase 07.3-03]` notes) because seam 6 had
only been implemented on the production `engine_adapter.SparqlAdapter`, not the
legacy one, at pin-bump time.

**Why it happens:** The pin bump and the two adapters' implementations are easy
to land in separate commits/plans; a `runtime_checkable` Protocol only fails
loudly at `isinstance()`/attribute-access time, not at import time, so the gap
is invisible until a test exercises the legacy adapter.

**How to avoid:** Implement `predicate_index()`/`predicate_prompt_section()` on
**both** `engine_adapter.SparqlAdapter` and `adapter.SparqlLanguageAdapter` in
the **same** plan/commit sequence that bumps the pin — never bump the pin
first and "come back" for the legacy adapter, even though that is exactly what
happened (and was fixed one plan later) in 07.3.

**Warning signs:** `pytest tests/nl2sparql/test_adapter.py` (legacy adapter's
own test file) failing with `AttributeError: 'SparqlLanguageAdapter' object has
no attribute 'predicate_index'` immediately after a pin bump — the exact
signature of the 07.3-02 regression.

### Pitfall 2: Assuming the raw ontology block alone will produce the lift

**What goes wrong:** A plan that just repeats `rdfs:domain`/`rdfs:range` triples
verbatim as the "new" predicate block risks measuring a null result, because
that information is already present in every prompt (verified: `grep` of
`corpus.yml`'s embedded `ontology:` block shows `pv:price`/`pv:amount`/
`pv:currency`/`pv:hasCategory`/`pv:ProductCategory` domain/range triples at
lines 54–349, well before `data_path:` at line 402).

**Why it happens:** D-02's phrasing ("derive... from the TBox... inject label +
domain + range") could be read as "restate the triples," when the actual lever
is the *imperative, example-driven* restatement (Pattern 5).

**How to avoid:** Verify the rendered block contains an explicit triple-pattern
example (`?x pv:price ?p . ?p pv:amount ?amt`) for value-object/category
predicates, not just a domain/range summary line — the example is the part not
already present anywhere else in the prompt.

### Pitfall 3: Over-scoping D-05 (query capture) as new plumbing

**What goes wrong:** Treating "capture generated SPARQL per case" as a new
data-flow addition risks touching more of `runner.py`/`NlPipeline` than
necessary.

**Why it happens:** It sounds like new instrumentation, but `CaseResult`
(`runner.py`, line ~52-58) **already** has an `actual: str` field populated
from `outcome.sparql` on every case (line ~594: `actual=outcome.sparql`). The
only place the SPARQL is dropped is `write_report()`'s JSON payload dict
literal (line ~720: `{"name": c.name, "passed": c.passed, "elapsed_ms":
c.elapsed_ms}` — no `"sparql"` key).

**How to avoid:** The D-05 fix is a one-key addition to that dict literal
(`"sparql": c.actual`), not a new field, new pipeline plumbing, or a schema
change. Verify by re-reading `write_report()` before scoping a bigger task than
needed.

### Pitfall 4: Re-authoring a QALD live zero-shot config that already exists

**What goes wrong:** D-03 describes "the first-ever live run of the powered
QALD-9-plus gate... zero-shot" as if the config needs to be created.

**Why it happens:** The config **already exists** —
`configs.yml`'s `openai-gpt4o-mini-qald9plus` entry (added in Phase 07.1,
`judge: canonical`, `corpus: vendored/qald9plus/corpus.yml`) is exactly this
config; it has simply never been **run** live (credentials-gated, human-run
only). The phase's job is to run it (a `checkpoint:human-action` task), plus
add the **new** `-predicate-grounded` sibling configs — not to author the
zero-shot one from scratch.

**How to avoid:** Diff `configs.yml` before scoping new-config tasks; only
`{scripted,openai-gpt4o-mini}-{ck25,qald9plus}-predicate-grounded` are net-new.

### Pitfall 5: Using `data_path`/instance-graph presence as the predicate-index gate

**What goes wrong:** Mirroring `runner.py`'s existing `if grounding_cfg and
data_ttl:` guard (entity grounding, which needs an instance graph) for the new
predicate config would silently produce `predicate_index=None` for QALD, since
QALD's `corpus.yml` has **no** `data_path:` key at all (confirmed: `grep
'^data_path:'` on QALD's corpus.yml returns nothing).

**Why it happens:** Copy-pasting the existing gate pattern without noticing
predicate grounding's source (`shared_ontology`, always present) differs from
entity grounding's source (`data_ttl`, present only for corpora that vendor an
instance graph).

**How to avoid:** Gate the new `predicate_grounding:` config block on
`shared_ontology` (always truthy for every corpus, including QALD), never on
`data_ttl`.
