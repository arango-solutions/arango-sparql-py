# Phase 07.6: NL→SPARQL relationship-path grounding — Research

**Researched:** 2026-08-07
**Domain:** NL→query engine seams (`arango_query_core.nl`), TBox class-connectivity graph build, bounded shortest-path retrieval, prompt composition
**Confidence:** HIGH — the design (D-1…D-10, D-01…D-04) is locked in SPEC.md/CONTEXT.md/the scope doc; this research verifies the exact structural template, integration points, and TBox facts the plan will bind against.

## Summary

Phase 07.6 adds one new engine seam, `ClassPathIndex` (seam-8), to `arango_query_core.nl`, mirroring `LabelIndex`/`PredicateIndex` (seam-6/7) byte-for-byte in construction discipline: frozen/caller-owned, stdlib-only, no memoization, `""`-on-no-match renderer contract. Unlike seam-6/7, seam-8's retrieval does **not** self-score against the question — it consumes anchor classes (from seam-6's already-retrieved `GroundedEntity.type`) and target predicates/classes (from seam-7's already-retrieved token-scorer hits), because D-02 explicitly delegates all question-matching to the seams already proven to work. This is the one structural place seam-8 does **not** mirror seam-6/7's shape, and it is the single most important thing for the planner to get right: `ClassPathIndex` takes pre-resolved anchor/target class IRIs, not a raw question string.

The graph-build precedent is `build_predicate_index` (`tests/nl2sparql/eval/grounding_index_builder.py:189-333`, this repo's 07.4 TBox walker) — a two-pass pyoxigraph query over `rdfs:domain`/`rdfs:range` declarations. `ClassPathIndex`'s build needs a third structural ingredient this walker doesn't have: `rdfs:subClassOf` traversal (D-9) and bidirectional (forward+inverse) edge storage (D-2), both **verified against the real CK25 TBox this session** (`tests/nl2sparql/eval/vendored/ck25/raw/prod-inst-schema.ttl`) — the canonical ck25-7 case (`Employee ⊑ Agent`, `memberOf` domain=`Agent`, `hasManager` domain=`Employee`) is a real, quoted fact in that file, not an assumption.

A critical, file:line-verified integration pitfall: `GroundedEntity.type` (seam-6's field the anchor class comes from) is populated as a **local name string** (`"Department"`), never a full class IRI — confirmed in `build_label_index` (`tests/nl2sparql/eval/grounding_index_builder.py:150-152`). `ClassPathIndex`'s anchor-lookup path must resolve on local names (or the adapter must map local-name → full IRI before calling into the index), exactly mirroring how `build_predicate_index` already keeps `domain`/`range` as rendered local names while joining internally on full IRIs (`grounding_index_builder.py:265-282`).

**Primary recommendation:** build `ClassPathIndex` in `arango_query_core/nl/grounding.py` (or a sibling module, e.g. `arango_query_core/nl/pathindex.py`) as a frozen, caller-owned class exposing `shortest_paths(anchor_classes, target_predicates, k=5) -> list[ClassPath]` and `format_prompt_section(paths, header=..., instruction=...) -> str`; build it from the same `rdfs:domain`/`rdfs:range`/`rdfs:subClassOf` Turtle walk `build_predicate_index` already performs, adding subclass-linked + inverse edges; wire it into both `SparqlAdapter` (`engine_adapter.py`) and `SparqlLanguageAdapter` (`adapter.py`) with a byte-identical parity test (mirrors `tests/nl2sparql/test_grounding_prompt_parity.py`); compose it after the entity block in `NLQueryEngine._system_prompt` (`arango_query_core/nl/engine.py:120-139`); add the additive `path_grounding:` config block to `runner.py`/`configs.yml`/`run_composed_sweep.py` mirroring `grounding:`/`predicate_grounding:` exactly; and gate the whole thing behind an always-on, no-key offline recall test mirroring `tests/nl2sparql/eval/test_grounding_recall.py`'s existing precedent (build index once, compare retrieved-vs-gold, assert a floor).

### Pattern 1: Frozen, caller-owned index (mirror `LabelIndex`/`PredicateIndex`)

**What:** `ClassPathIndex.__init__(self, paths_or_graph)` / `.from_items(...)` classmethod, no file I/O, no memoization inside the class.
**When to use:** Always — this is the shared contract across seam-6/7/8, verified byte-identical in `LabelIndex`/`PredicateIndex` (`grounding.py:162-184`, `249-278`).
**Example (existing seam-6, the exact shape to mirror):**
```python
# Source: arango_query_core/nl/grounding.py:162-184
class LabelIndex:
    def __init__(self, entities: list[GroundedEntity]) -> None:
        self._entities: list[GroundedEntity] = list(entities)

    @classmethod
    def from_items(cls, items: list[GroundedEntity]) -> LabelIndex:
        return cls(items)

    def retrieve(self, question: str, k: int = 20) -> list[GroundedEntity]:
        return _token_substring_retrieve(self._entities, lambda e: e.labels, question, k)
```

### Pattern 2: Two-pass TBox walk with subclass + inverse extensions (D-9, D-2)

**What:** `build_predicate_index`'s existing two-pass pyoxigraph query (`grounding_index_builder.py:189-333`) is the base graph-build precedent. `ClassPathIndex`'s eval-side builder needs the SAME Pass-1 declared-property walk (kind/label/domain/range), PLUS:
- a `rdfs:subClassOf` closure query per class (new — build_predicate_index deliberately does NOT do this: "this file MUST NOT walk any class-hierarchy inheritance predicate here" per its own docstring, `grounding_index_builder.py:213-215`, because predicate *shape classification* would over-fire on it; `ClassPathIndex`'s connectivity graph is a DIFFERENT consumer with the OPPOSITE need — it must walk subclass, or ck25-7 is unreachable)
- storing BOTH directions of every object property edge (D-2)

**Verified against the real CK25 TBox this session** (`tests/nl2sparql/eval/vendored/ck25/raw/prod-inst-schema.ttl`):
```turtle
# Lines 64-69 — the canonical D-9 case
pv:Employee a owl:Class ;
  rdfs:label "Employee"@en ;
  ...
  rdfs:subClassOf pv:Agent .

# Lines 172-178
pv:hasManager a owl:ObjectProperty ;
  ...
  rdfs:domain pv:Employee ;
  ...
  rdfs:range pv:Manager .

# Lines 204-210
pv:memberOf a owl:ObjectProperty ;
  ...
  rdfs:domain pv:Agent ;
  ...
  rdfs:range pv:Department .
```
Without subclass-aware linking, `memberOf` (domain `Agent`) and `hasManager` (domain `Employee`) sit on disconnected nodes in a naive exact-class graph — exactly the miss the Step-0 spike found (scope doc §9). With subclass-aware linking (`Employee ⊑ Agent`), an `Employee`-typed anchor can traverse BOTH edges, producing the gold join `?person pv:memberOf <Dept> . ?person pv:hasManager ?result` (verified verbatim in `candidates_dump.json` line 52, case `ck25-7`).

**D-2 (inverse) verified:** `pv:hasCategory` (domain `Product`, range `ProductCategory`, lines 156-162) only has a forward edge Product→ProductCategory. Case `ck25-12`'s gold anchors on `ProductCategory` (`<prod-cat-Compensator>`) and needs to reach `Product`/`Hardware` — only reachable via the INVERSE of `hasCategory`. Confirmed in `candidates_dump.json` line 87-88 (gold: `?hardware pv:hasSupplier ?result . ?hardware pv:hasCategory <...Compensator>`).

**D-10 (self-revisit) verified:** `pv:compatibleProduct` is a genuine self-loop —
```turtle
# Lines 124-130
pv:compatibleProduct a owl:ObjectProperty ;
  ...
  rdfs:domain pv:Product ;
  ...
  rdfs:range pv:Product .
```
A naive simple-path DFS/BFS that forbids revisiting a node type would treat `Product` as already-visited and drop this edge — case `ck25-35`'s gold path (`?prod pv:compatibleProduct ?compatible`, then both sides join to `pv:price`) needs the self-loop to survive.

**D-1/depth precedent verified:** the two depth-4 misses (`ck25-47`/`ck25-48`) are a genuine 4-class-hop chain — verified via the object-property chain: `pv:hasBomPart` (domain `BillOfMaterial`, range `BomPart`, lines 148-154) → `pv:hasPart` (domain `BomPart`, range `Product`, lines 180-186) → `pv:hasSupplier` (domain `Product`, range `Supplier`, lines 196-202) → `pv:country` (domain `Supplier`, range `dbo:Country`, lines 132-138, an EXTERNAL DBpedia class — the graph build must treat this as an opaque node, no special-casing). SPEC.md locks depth ≤3 and logs these two cases as an accepted known limitation — do NOT relax depth to 4 (out of scope).

### Pattern 3: Prompt composition point (engine)

**What:** `NLQueryEngine._system_prompt` builds sections in a fixed list and joins non-empty ones.
**Example (existing, showing exactly where the new block inserts):**
```python
# Source: arango_query_core/nl/engine.py:120-139
def _system_prompt(self, question: str, schema_context: str) -> str:
    sections = [self.adapter.grammar_prompt_section(schema_context)]
    ... # few-shot (seam 2)
    grounding = self.adapter.grounding_index()          # seam 6
    if grounding is not None:
        block = self.adapter.grounding_prompt_section(question, grounding, k=self.grounding_k)
        if block:
            sections.append(block)
    predicates = self.adapter.predicate_index()          # seam 7
    if predicates is not None:
        pred_block = self.adapter.predicate_prompt_section(question, predicates, k=self.predicate_k)
        if pred_block:
            sections.append(pred_block)
    # <-- seam-8 (ClassPathIndex) composes HERE, after the seam-7 block,
    #     following the exact same "index is not None -> render -> append if non-empty" shape
    return "\n\n".join(s for s in sections if s)
```
Add a `path_k: int = 5` field to `NLQueryEngine` (mirrors `grounding_k`/`predicate_k`) and a `paths = self.adapter.path_index()` / `if paths is not None: ...` block, identical shape.

### Anti-Patterns to Avoid
- **Reimplementing a token scorer inside `ClassPathIndex`:** D-02 requires reusing seam-6/7's already-retrieved hits. A second hand-rolled scorer duplicates `_token_substring_retrieve` and risks re-introducing CR-01-style dump/retrieve confusion.
- **Rendering a directed A→B→C walk for join/star cases:** D-04 explicitly locks the shared-variable join form for ck25-7/35-shaped queries. A literal `<Dept> -memberOf-> ?p -hasManager-> ?m` chain misrepresents what's actually a two-triple join on `?p`.
- **Dumping the whole class graph "just in case":** this is precisely the 07.4 distraction regression (`all` arm 12/49 < `g+f` 16/49, `.planning/research/relationship-path-grounding-scope.md` §1). The ≤5-path global-pool budget (D-03) is the specific control.

|---------|-------------|--------------|-----|
| Question-to-class/predicate token matching | A second substring scorer inside `ClassPathIndex` | Reuse seam-6's `LabelIndex.retrieve()` (for anchor types) and seam-7's `PredicateIndex.retrieve()` (for targets) unchanged, via `_token_substring_retrieve` | D-02 explicitly delegates this; `_token_substring_retrieve` is already shared between seam-6/7 (`grounding.py:97-146`) — a third copy would fork the ranking rule |

## Common Pitfalls

### Pitfall 1: The 07.4 distraction regression re-emerging
**What goes wrong:** surfacing too much schema context distracts the LLM into worse queries even when the surfaced content is technically correct.
**Why it happens:** a large "known predicates" or "known paths" block competes for attention with the actual question-relevant hint, and the model latches onto irrelevant structure.
**How to avoid:** enforce the ≤5-path GLOBAL pool (D-03) at the `format_prompt_section` level — a hard cap regardless of how many (anchor, target) pairs exist; add a unit test asserting the rendered block never contains more than 5 path lines.
**Warning signs:** the credentialed sweep's `all vs g+f`-style contrast shows a net-negative delta despite individual case wins (exactly the pattern `all vs g+f` showed in 07.4/07.5 composed evaluation).

### Pitfall 2: Naive exact-class graph silently drops the canonical case
**What goes wrong:** without D-9 (subclass-aware nodes), `ClassPathIndex` builds a graph where `Employee` and `Agent` are disconnected classes even though `Employee ⊑ Agent` — and the ck25-7 "manager of a department" case (the lever's own namesake) never recovers.
**Why it happens:** `rdfs:domain`/`rdfs:range` declarations are per-exact-class; a predicate declared with `domain: Employee` never appears when walking from an `Agent`-typed anchor unless subclass links are walked too.
**How to avoid:** walk `rdfs:subClassOf` and either (a) union a subclass's edges onto its superclass node, or (b) union a superclass's edges onto every subclass node — verified this is required against the real TBox (Pattern 2 above); write a unit test using exactly the `Employee ⊑ Agent` / `memberOf` domain=`Agent` / `hasManager` domain=`Employee` shape as a synthetic fixture (mirrors `test_nl_grounding.py`'s existing small-fixture-per-behavior style).
**Warning signs:** the R4 recall gate misses specifically the cases the scope doc's Step-0 spike already identified (ck25-7, and by extension any case whose anchor/target classes differ by a subclass hop).

### Pitfall 3: `GroundedEntity.type` is a local name, not a full IRI
**What goes wrong:** anchor-class resolution (D-02: "distinct `rdf:type` among the seam-6 grounded matches") reads `GroundedEntity.type`, which is populated as `raw_type.rsplit("/", 1)[-1].rstrip(">")` — e.g. `"Department"`, never `"http://ld.company.org/prod-vocab/Department"`.
**Why it happens:** `build_label_index` (`tests/nl2sparql/eval/grounding_index_builder.py:150-152`, quoted verbatim: `raw_type = row.get("type")` then `entity["type"] = raw_type.rsplit("/", 1)[-1].rstrip(">")`) deliberately renders a local name for the prompt's `(Department)` gloss — it was never designed to be a join key back into a TBox graph.
**How to avoid:** either (a) key `ClassPathIndex`'s internal graph nodes by LOCAL NAME (consistent with how `GroundedPredicate.domain`/`.range` are already local names, per `build_predicate_index`'s `_local_name()` helper, `grounding_index_builder.py:274-276`) — the simplest fix, since local names are unique within a single-vocabulary TBox like CK25 — or (b) have the adapter resolve local-name → full-IRI before calling into `ClassPathIndex`. Given seam-7 already normalizes to local names throughout, (a) is the path of least resistance and keeps `ClassPathIndex`'s public surface consistent with seam-7's.
**Warning signs:** anchor resolution silently returns zero paths for every case (a same-shape bug to seam-7's own CR-01 "widening k alone doesn't dump" defect — an integration mismatch that looks like "no signal" rather than "wrong code").

### Pitfall 4: `ClassPathIndex` is not a self-contained `retrieve(question, k)` scorer
**What goes wrong:** building `ClassPathIndex.retrieve(question, k)` in the seam-6/7 shape (question in, ranked items out) would require re-deriving anchor/target classes from the raw question text inside the index itself — duplicating seam-6/7's already-proven retrieval.
**Why it happens:** the instinct to "mirror seam-6/7 exactly" is right for construction/renderer contract, but D-02 is explicit that anchor/target resolution reuses seam-6/7's OWN retrieval outputs, not a third independent question-parse.
**How to avoid:** design `ClassPathIndex`'s public retrieval method to take already-resolved class/predicate identifiers (`shortest_paths(anchor_classes: list[str], targets: list[str], k=5)`), NOT a question string. The adapter's `path_prompt_section(question, path_index, k=...)` implementation is where the seam-6/7 `.retrieve(question, ...)` calls happen, feeding their outputs into `path_index.shortest_paths(...)`.
**Warning signs:** a `ClassPathIndex` unit test that requires a full question string to exercise basic graph-traversal logic is a sign the abstraction boundary has drifted from D-02.

### Pitfall 5: `NlPipeline` (project-side orchestrator) is a required, not-yet-listed integration point
**What goes wrong:** `arango_sparql/nl2sparql/pipeline.py`'s `NlPipeline.__init__`/`.run()` (verified, `pipeline.py:128-199`) explicitly threads `grounding_k`/`grounding_index` and `predicate_k`/`predicate_index` from its own constructor into `SparqlAdapter(...)` and `NLQueryEngine(...)` — this is a THIRD wiring point beyond the two adapters (`engine_adapter.py`'s `SparqlAdapter` and `adapter.py`'s `SparqlLanguageAdapter`) and the eval harness (`runner.py`). It is not named in CONTEXT.md's canonical_refs but is structurally required for `path_k`/`path_index` to reach the engine when driven through `NlPipeline` (the eval harness's `runner.py:601-612` calls `NlPipeline(...)` directly, not `SparqlAdapter` alone).
**Why it happens:** `NlPipeline` is the production orchestration layer sitting between the eval config and the two adapters; seam-6/7's own history shows this file needed updating in both the 07.3 and 07.4 phases (its docstring at `pipeline.py:106-124` explicitly narrates both additions).
**How to avoid:** add `path_k: int = 5` and `path_index: ClassPathIndex | None = None` to `NlPipeline.__init__` (mirroring `predicate_k`/`predicate_index`, `pipeline.py:139-140,162-163`) and thread them into the `SparqlAdapter(...)` and `NLQueryEngine(...)` constructions inside `.run()` (`pipeline.py:184-199`).
**Warning signs:** `runner.py`'s new `path_index=path_index` kwarg to `NlPipeline(...)` raises `TypeError: unexpected keyword argument` if this file is missed — a compile-time-visible signal, not a silent miss, but still an extra task the plan must not omit.

### Pitfall 6: Engine pin-bump sequencing (D-01)
**What goes wrong:** bumping `pyproject.toml`'s `arango-query-core` git pin before the recall gate is proven green against the pushed commit risks shipping a broken/incomplete engine seam that this repo's CI then depends on.
**Why it happens:** the natural order is "write code, test locally, push, bump pin" — but "test locally" here means running R4's recall gate against a LOCAL EDITABLE install of the engine checkout (not yet pushed), then re-verifying against the PUSHED commit before the pin bump (07.5-06's exact sequence, `STATE.md` line 222: "Consumer verified against a local-editable engine BEFORE the push").
**How to avoid:** sequence: (1) build `ClassPathIndex` in `~/dev/arango-query-core`, (2) run engine unit tests there, (3) `pip install -e ~/dev/arango-query-core` (or uv equivalent) in this repo and run R4 locally against the editable checkout, (4) push to BOTH remotes (`arthur`, `origin` — verified via `git remote -v` in the checkout), (5) `git ls-remote` both remotes to confirm the pushed SHA is visible, (6) bump `pyproject.toml:67,77` AND `uv.lock`, (7) re-run R4 against the pinned (non-editable) install as a final confirmation.
**Warning signs:** skipping step 5 (the ls-remote verification) — 07.5-06's own precedent calls this out explicitly as a prior lesson ("ls-remote-verified on both BEFORE uv lock").

1. **What are the exact 16 "empty-result, right-entity-wrong-path" gold cases, precisely?**

2. **Exact `ClassPathIndex` public method names/signatures.**
   - What we know: the constructor/renderer CONTRACT is locked (mirror `LabelIndex`/`PredicateIndex`: frozen, caller-owned, `""`-on-no-match). The RETRIEVAL signature is not — it must take pre-resolved anchor classes + targets (Pitfall 4), not a question string, which is a genuine departure from seam-6/7's shape.
   - What's unclear: whether to name it `shortest_paths(anchors, targets, k)` returning a list of a new `ClassPath` dataclass, or fold path-finding directly into `format_prompt_section(anchors, targets, ...)` the way `retrieve`+`format_prompt_section` are two separate methods in seam-6/7.
   - Recommendation: keep the two-method split (retrieval separate from rendering) for testability — mirrors seam-6/7's own `retrieve()`/`format_prompt_section()` split, which lets engine unit tests assert on raw paths without string-matching rendered prose.
