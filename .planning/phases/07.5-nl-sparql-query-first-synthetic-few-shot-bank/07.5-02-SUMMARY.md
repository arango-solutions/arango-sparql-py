## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Subject-side domain-type constraint silently zeroed the highest-value shapes**

- **Found during:** Task 2, first full pipeline run against real CK25 data
- **Issue:** Every `build_sparql` closure's first draft included `?x a <domain_iri>` (or `?result a <domain_iri>`) as a correctness/precision safeguard. Empirically, CK25's TBox declares `rdfs:domain pv:Product` for `hasCategory`/`hasSupplier`/`hasProductManager`/`compatibleProduct` and `rdfs:domain pv:Agent` for `memberOf`/`areaOfExpertise` -- but `pv:Product` and `pv:Agent` have ZERO instances directly typed as such in `prod-inst.ttl` (only their concrete subclasses `pv:Hardware`/`pv:Service`/`pv:Employee`/`pv:Manager` are ever typed). The constraint therefore matched nothing, dropping `value_object` and `two_hop` to 0 kept examples and severely undercounting `category_filter`/`scalar_count`/`grouped_aggregation`.
- **Fix:** Removed the subject-side type constraint from every closure and its matching label-sampling pattern; kept the RANGE-side constraint where it remains load-bearing (category_filter/scalar_count/two_hop's label anchor). Cross-checked against the VALIDATED spike bank (`.planning/spikes/001-ck25-thin-fewshot-signal/ck25_thin_fewshot_bank.yml`), whose own hand-written `hasCategory`/`hasSupplier` queries never included a domain type triple either -- confirming this is the historically-correct pattern, not a new risk.
- **Files modified:** `tests/nl2sparql/eval/bank_generator.py`
- **Verification:** Re-ran `generate_bank_with_report` against real CK25 data: total examples 30 -> 77, `value_object` 0 -> 2, `two_hop` 0 -> 8 kept; re-ran full `verify_generated_bank.py` offline gate (100% green, no leakage, no instance-namespace IRI) and `test_bank_generator.py` (37/37 passing).
- **Committed in:** `89ffb0a` (Task 2 commit)
