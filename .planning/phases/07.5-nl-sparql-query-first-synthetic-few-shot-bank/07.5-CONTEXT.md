# Phase 07.5: NL→SPARQL query-first synthetic few-shot bank - Context

**Gathered:** 2026-07-30
**Status:** Ready for planning

<domain>
## Phase Boundary

A build-time generator that, given any ontology's TBox (+ representative instance data),
produces a per-ontology `(question, gold-SPARQL)` few-shot bank **query-first**, loaded through
the existing BM25 `FewShotIndex` seam so NL→SPARQL specializes to any new ontology without
hand-curation. Validated by the *same generator* run across two independent ontologies
(CK25 corporate + QALD DBpedia) on held-out human questions, graded mechanistically + directionally.

</domain>

<decisions>
## Implementation Decisions

### Generator home & sequencing
- **D-01:** Build in **three explicit stages, spike-gated.** **Stage 0 (spike):** thin slice — 2–3
  shapes, CK25 only, hand-built generated examples — does adding them move *any* held-out CK25 case?
  The full build is gated on a non-null spike (run `/gsd-spike` before committing the multi-wave plan).
  **Stage 1 (eval prototype):** full generator as pure functions in `tests/nl2sparql/eval/` (mirrors
  `build_predicate_index`/`grounding_index_builder`); run the CK25+QALD measurement per SPEC. **Stage 2
  (engine promotion, ONLY if the SPEC adopt bar clears):** port the reusable construction core to an
  `arango_query_core` seam (Cypher inherits; pin bump). **The eval prototype validates the HYPOTHESIS;
  the engine promotion is the PRODUCT deliverable** (build-time integration for real ontology
  onboarding) — do not conflate a clean CK25/QALD measurement with a working production capability.
  The generated bank loads through the existing engine BM25 `FewShotIndex` regardless — no new engine
  code is needed to *consume* it.

### v1 template ambition
- **D-02:** Target the **full ≥7 shapes including the hard compositional ones** (COUNT / top-N / OFFSET /
  negation / 2-hop) — easy single-predicate shapes alone would reinforce what the model already gets
  right (~0 lift). Two guards against the filter silently gutting coverage: (a) **per-shape YIELD is a
  first-class output** — report how many valid examples each shape produced per ontology, so a hard
  shape yielding ~0 is a *measured finding*, not a hidden gap; (b) the hard shapes need **richer TBox
  signal than 07.4's 4-way classification** — derive numeric/orderable-literal detection (ranking) and
  expected-but-optional-relation detection (negation); if a shape can't be built non-empty + faithful
  for an ontology, **drop it with a logged reason** (counts honestly against shape-coverage).

### Paraphrase & faithfulness
- **D-03:** Same **NL2SPARQL provider** (`OpenAICompatibleClient`, human-held key), **K=3** paraphrases
  (config knob). Faithfulness PRIMARY guard = check each paraphrase against the **question template's
  known semantic slots** (does it preserve the top-N-descending / filter intent?) — the paired template
  is the ground truth; the LLM-judge is only a **secondary sample check**, not the primary guard.
  Explicitly: bank generation has a **build-time LLM dependency** (paraphrase + judge), so "auto-onboard
  any ontology" means *auto given LLM access at build time*, not hands-free — the onboarding pipeline
  needs an LLM key.

### QALD data-binding
- **D-04:** **CK25 richly data-bound** (`prod-inst.ttl`); **QALD best-effort / TBox-only.** Do NOT build a
  DBpedia instance snapshot from QALD's gold-query entities — that leaks test entities into examples
  (entity-level contamination the shape overlap audit wouldn't catch). The cross-ontology generalization
  claim rests on "**the same generator RUNS on DBpedia's TBox and emits structurally-valid, faithful
  examples**"; the accuracy **lift is measured primarily on CK25** (rich binding). A *leakage-safe general*
  DBpedia instance slice may be used for QALD binding if cheaply available; otherwise QALD examples are
  structurally-valid-but-thin — an accepted, documented limitation (QALD's bottleneck is orthogonal
  entity grounding anyway).

### Measurement refinement
- **D-05:** The overlap audit checks **both query-shape AND entity-level** overlap between the generated
  bank and the held-out test set (entity axis added because of D-04's leakage risk); report the lift
  excluding near-duplicates on **both** axes.

### Claude's Discretion
- Exact template representation/DSL, bank file naming, slot-value sampling strategy, per-shape-yield
  report format, and the spike's exact 2–3 shapes — researcher/planner choice within the above.

</decisions>

## Existing Code Insights

### Reusable Assets
- `build_predicate_index` (07.4): mechanical TBox shape classification — the seed for template slot-filling; extended with numeric/optional-relation detection for hard shapes (D-02).
- `FewShotIndex`/`BM25Retriever`: consume the generated bank unchanged (proven +19pt).
- `runner.run` + `oxi_query`: in-process pyoxigraph execution — reused both as the generation-time non-empty filter (D-02) and the measurement judge; `_stable_repr`/`_skeleton` give the canonical shape abstraction for overlap (D-05).
- `OpenAICompatibleClient` / `_client_for`: provider plumbing for paraphrase + faithfulness judge (D-03).
- `test_fewshot_bank_disjoint.py`: existing disjointness discipline to extend.

### Established Patterns
- Eval-only builders live in `tests/nl2sparql/eval/`; engine seams live in `arango_query_core` (Cypher inherits) — the 07.3/07.4 sequencing D-01 follows.
- Credentialed live sweeps are human-run (`NL2SPARQL_API_KEY` human-held); scripted/no-network is the CI default; W3C DAWG ≥96.4% + transpiler package unchanged are hard non-regression invariants.

### Integration Points
- Generated `<ontology>_fewshot_bank.yml` → `FewShotIndex` → appears in `NLQueryEngine._system_prompt` `## Examples`; an eval config arm points at it (mirrors the existing dense/bm25 arms).
