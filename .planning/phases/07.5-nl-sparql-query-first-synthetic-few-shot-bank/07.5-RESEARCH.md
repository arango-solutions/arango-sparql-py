## Summary

Phase 07.5 builds a **build-time generator** that emits a per-ontology `(question, gold-SPARQL)` few-shot bank from an ontology's TBox (+ instance data), so NL→SPARQL specializes to any new ontology without hand-curation. Everything the generator *consumes* and everything that *measures* it already exists and is proven: the 07.4 TBox walker (`build_predicate_index`), the pyoxigraph execution oracle (`oxi_query`), the BM25 `FewShotIndex` seam (+19pt, unchanged), the canonical-algebra shape abstraction (`runner._canonical`/`_skeleton`), the paired-stats helpers, and the human-run credentialed-sweep harness pattern (`run_spike.py`). The phase is therefore **mostly new construction logic wired into a mature, well-understood eval spine** — low integration risk, with the genuine uncertainty concentrated entirely in whether the generated (not hand-built) bank reproduces the spike's lift.

The Stage-0 spike (001) is **VALIDATED and load-bearing**: 9 hand-built name-anchored examples across 3 shapes lifted held-out CK25 from 5/49 to 15/49 (McNemar b=11, c=1, p=0.0063; bootstrap +0.204, CI [+0.082, +0.327]). It hands the full build three carry-forward requirements: (1) **name-anchored composition** (`?d pv:name "Engineering"`, never a hardcoded IRI) is the winning example form — it sidesteps the orthogonal entity-grounding bottleneck and is what generalized; (2) **grouped aggregation (GROUP BY/HAVING) is a distinct shape** from scalar COUNT — the lone regression (ck25-30) was a HAVING case scalar-COUNT examples distracted; (3) the **"zero regressions" adopt bar is a real constraint** — one distraction loss appeared even in a 9-example bank.

**Primary recommendation:** Build Stage 1 as a pure-function module `tests/nl2sparql/eval/bank_generator.py` structured as a **typed template catalog** (dataclass templates carrying named semantic slots so D-03's faithfulness-by-slot check is mechanical), driven by an **extended `build_predicate_index`** (add orderable-literal and optional-relation signals), with data-binding + execution-filter via the same `oxi_query` engine the judge uses, and a generalized offline validity gate (promote `spike/verify_bank.py` into `verify_generated_bank.py`). Emit `<ontology>_fewshot_bank.yml` in the exact `version:`+`examples:` shape `FewShotIndex` already loads. Measure with a `run_spike.py`-shaped human-run paired sweep. Treat **grouped aggregation as a 9th shape**. Gate Stage 2 (engine promotion) strictly behind the SPEC adopt bar.

## Generator Architecture

### Template representation — RECOMMENDATION: typed dataclass catalog (not a string DSL)

Represent each shape as a `ShapeTemplate` dataclass, registered in an ordered catalog:

```python
# tests/nl2sparql/eval/bank_generator.py  (illustrative — not verbatim)
@dataclass(frozen=True)
class ShapeTemplate:
    name: str                        # "top_n", "grouped_aggregation", "negation", ...
    applies: Callable[[GroundedPredicate, "PredicateIndex"], bool]   # TBox-signal gate
    build_sparql: Callable[[Binding], str]      # slot-filled name-anchored SPARQL
    question_template: str           # "what is the {superlative} {C} by {P}?"
    semantic_slots: tuple[str, ...]  # ("category", "order_predicate", "direction") — D-03 ground truth
    intent_lexicon: tuple[str, ...]  # ("most", "least", "highest", ...) — paraphrase guard
```

**Rationale (Claude's Discretion, HIGH confidence):**
- A Jinja/string-template DSL adds a dependency and hides slot semantics in text. D-03's *primary* faithfulness guard needs the semantic slots to be **first-class, machine-readable data** (which category filler, which ordering direction, which shape-intent) — a typed dataclass makes the slot-preservation check a trivial set/dict comparison, not a regex over rendered text.
- Mirrors the codebase's established style: pure functions + dataclasses in `tests/nl2sparql/eval/`, `GroundedPredicate` shape classification, `CaseResult`/`Report`. Zero new deps; trivially unit-testable offline.
- The catalog is **schema-agnostic** by construction: `applies`/`build_sparql` read only `GroundedPredicate` fields (kind, domain, range, shape, shape_detail) and sampled data — never a hardcoded vocabulary term (D-02 / SPEC constraint; the walker's own docstring forbids per-schema hints).

**Bank file naming (Discretion):** `tests/nl2sparql/eval/vendored/<ontology>/generated_fewshot_bank.yml`. Keep it beside the corpus so the corpus's `data_path`/`ontology` are co-located. Emit only `version:` + `examples:` (question/query). Do **not** copy the `ontology:` block into it — that would trip `test_bank_ontology_matches_corpus`, which is specific to the *curated* `fewshot_bank.yml`; the generated-bank overlap audit is a **new** test (W4), not that exact one.

### The 07.4-walker extension (D-02)

`build_predicate_index` today classifies each predicate `literal / value_object / category_instance / linked_entity` purely from `rdfs:domain`/`rdfs:range` (two-pass, mechanical, no per-schema hints). Add two **mechanical** signals, same discipline:

1. **Orderable-literal detection (ranking → top-N / OFFSET / grouped-HAVING).** A `DatatypeProperty` whose `rdfs:range` is an ordered XSD type (`xsd:decimal`, `xsd:integer`, `xsd:float`, `xsd:double`, `xsd:dateTime`, `xsd:date`) is `orderable`. Purely from the range IRI — no term names. CK25 orderables: `amount`, `weight_g`, `height_mm`, `width_mm`, `depth_mm`, `reliabilityIndex`, `quantity` (all `xsd:decimal`); `pv:name`/`addressCountry` (`xsd:string`) are **not** orderable. This is what reaches top-N/OFFSET where the model actually fails.
2. **Expected-but-optional-relation detection (negation → FILTER NOT EXISTS).** An `ObjectProperty` `P` with domain `C` where the instance data contains **both** `C`-instances that have `P` and `C`-instances that lack it. This is inherently **data-driven** (a probe against the store), consistent with the execute-to-drop-empties discipline: it guarantees `FILTER NOT EXISTS { ?x P ?y }` returns non-empty. On a TBox-only ontology (QALD) this signal is unavailable → the negation shape is **dropped with a logged reason** for QALD (honest yield, D-02).

Keep both signals as new fields on `GroundedPredicate` (or a sibling struct) — additive, so 07.4's existing consumers are byte-unchanged.

### Data-binding + execution-filter

- **Slot sampling.** For each candidate template × predicate, enumerate real slot fillers by querying the instance store with `oxi_query` (e.g. all `pv:ProductCategory` names; all `pv:Department` names; all `Supplier` countries). Recommend **bounded, deterministic sampling** (cap per shape, seeded `random.Random`) so regeneration is reproducible and build cost stays bounded (Q7). Prefer **high-cardinality / discriminating** fillers.
- **Name-anchored emission (spike carry-forward #1, MUST).** Resolve every entity slot via a label/name triple (`?c pv:name "Crystal"`, or `?x rdfs:label "..."`), **never** a hardcoded instance IRI. The generator needs the per-class label predicate — reuse the `label_predicates` concept (`rdfs:label` covers `pv:name` on CK25, verified 0 counterexamples in `_build_label_map`). Under the answer-set execution judge a name-join returns the same rows as an IRI-hardcoded gold, and it stays algebra-disjoint from every held-out gold (leakage-safe) — this is exactly the pattern that generalized in the spike.
- **Execution non-empty filter (REQ-2, MUST be 100%).** Instantiate → `oxi_query` against the store → keep only non-empty (`rows≥1` / `true` / meaningful count). Reuse `load_store_from_string(data_ttl)` once, outside the per-candidate loop.
- **Top-N / OFFSET strict-extremum gate (spike lesson).** For ranking shapes, run the spike's probe pattern (drop `LIMIT`, `ORDER BY DESC/ASC`, read top-2/3) and **require a strictly-unique extremum** so `LIMIT 1` / `OFFSET 1` is deterministic. The spike caught `weight_g` saturated at 20.0 across every category — a **bad ranking attribute**; the generator must detect and drop saturated/tied orderables per-ontology (counts against yield).

### Paraphrase + faithfulness-guard (D-03)

- **Provider.** `OpenAICompatibleClient(provider="openai", model="gpt-4o-mini")`, `.generate(messages: list[dict]) -> LLMResponse` (`.content`), reading `NL2SPARQL_API_KEY`. **K=3** (config knob). Human-run (credentialed); offline tests use `ScriptedLLMClient`.
- **Primary guard = slot preservation (offline, deterministic).** For each paraphrase, verify it preserves the template's `semantic_slots` — the literal fillers (category "Engineering", country "India", ordering direction) and the shape's `intent_lexicon` (top-N ⇒ a superlative token; COUNT ⇒ "how many"/"number of"; negation ⇒ "without"/"no"/"lacking"; grouped-agg ⇒ a per-group + threshold phrasing). The paired template is ground truth; a paraphrase that drops or flips a slot is rejected and regenerated/dropped. This is pure and unit-testable — **the primary guard, per D-03**.
- **Secondary = LLM-judge sample check (human-run).** On a random ≥20-pair sample, an LLM-judge (or human) confirms question↔query match ≥95% (REQ-3). Sample only — never the primary guard.
- **Honest caveat:** "auto-onboard any ontology" means *auto given LLM access at build time*, not hands-free (D-03). The onboarding pipeline has a build-time LLM dependency.

## Shape Catalog

Target **9 shapes** (comfortably ≥7; separates grouped aggregation from scalar COUNT per the spike carry-forward). Per-shape YIELD is a first-class report output — a hard shape yielding ~0 is a *measured finding*, not a hidden gap (D-02).

| # | Shape | SPARQL skeleton (name-anchored) | TBox signal it needs | Construction notes | Yield risk |
|---|-------|-------------------------------|---------------------|--------------------|-----------|
| 1 | **lookup** | `?x pv:name "V" . ?x P ?result` | any predicate on a labeled class | easiest; alone reinforces what the model gets right (~0 lift) — include but don't over-weight | low |
| 2 | **value-object** | `?x pv:name "V" . ?x price/amount ?result` (extra hop) | `value_object` shape (07.4) + its datatype child | uses `shape_detail` (label,range) pairs | low |
| 3 | **category-filter** | `?c pv:name "Crystal" . ?p pv:hasCategory ?c` | `category_instance` / `linked_entity` | name-anchored category; high value | low |
| 4 | **scalar COUNT** | `SELECT (COUNT(DISTINCT ?x) AS ?result) WHERE {...}` | any countable pattern | spike-proven (ck25-13) | low |
| 5 | **grouped aggregation** ⚠️ | `SELECT ?g (COUNT(?x) AS ?n) ... GROUP BY ?g HAVING(?n > K)` | groupable category + countable member | **DISTINCT shape** — the ck25-30 regression proves scalar-COUNT coverage does NOT cover HAVING and can distract it (spike carry-forward #2). Threshold K must be data-bound so the group survives non-empty | **medium** — needs a K with ≥1 surviving group |
| 6 | **top-N (ORDER BY+LIMIT)** | `... ?x P ?v ORDER BY DESC(?v) LIMIT 1` | **orderable** literal (new signal) | strict-unique extremum gate; drop saturated attrs (weight_g lesson) | **medium** — ties/saturation kill candidates |
| 7 | **OFFSET ("2nd most …")** | `... ORDER BY DESC(?v) LIMIT 1 OFFSET 1` | orderable literal | needs ≥2 strictly-ordered values | **medium** |
| 8 | **negation (FILTER NOT EXISTS)** | `?x a C . FILTER NOT EXISTS { ?x P ?y }` | **optional-relation** (new, data-driven) | needs both P-present and P-absent C-instances; **unavailable on TBox-only QALD → dropped w/ logged reason** | **high on QALD** (no instances, D-04) |
| 9 | **2-hop join** | `?c pv:name "V" . ?p pv:hasCategory ?c . ?p pv:hasSupplier ?s` | two chained `linked_entity`/object props | spike's richest bucket (12/12 failing on CK25); highest-value | low on CK25 |

**Grouped-aggregation-vs-scalar-COUNT question — RESOLVED: separate them.** The spike's single regression (ck25-30, `GROUP BY … HAVING(COUNT > 5)`) is direct evidence that scalar-COUNT examples *distract* a HAVING case. Treating #5 as its own shape (with its own retrievable examples) is the mitigation the carry-forward calls for, and it makes the "zero regressions" adopt bar attainable.

**QALD expected yield (D-04, HIGH confidence from 07.4-03):** DBpedia subset = 75 classes, 250 properties (88 object, 162 datatype), **0 instance triples**. Walker degrades object-property ranges to `category_instance` (0 value_object). Data-driven shapes (negation #8; strict-extremum top-N/OFFSET #6/#7 which need real values) will yield **~0 on QALD** — an accepted, documented limitation. QALD banks are structurally-valid-but-thin; the generalization claim is "same generator RUNS + emits valid examples," not "lifts QALD."

## Measurement & Overlap-Audit Design (D-05, REQ-6)

Reuse the eval spine wholesale — this is the phase's lowest-risk part.

- **Shape overlap.** Use `runner._canonical` (alpha-equivalent canonical algebra) and `runner._skeleton` / the disjoint test's `_skeleton` (literals/URIs abstracted to `?LIT`/`?URI`). A generated example whose skeleton equals a held-out gold's skeleton is a near-duplicate-shape. Extend `test_fewshot_bank_disjoint.py` to run over the *generated* bank (its existing 3-way check — normalized question, canonical algebra, skeleton — is exactly the seed).
- **Entity overlap (new, D-04 leakage axis).** Extract the literal fillers / IRIs from each generated example and from each held-out gold; report the intersection. The spike's leakage discipline (entity-disjoint departments/categories/countries) is the target: Engineering/Procurement/Crystal/India in the bank, never Data Services/Marketing/Oscillator/France (the held-out fillers).
- **Directional lift (human-run credentialed sweep).** Mirror `run_spike.py`: monkeypatch-isolated `run_generated_sweep.py` running a **generated-bank arm** vs a **fresh same-session zero arm** over the held-out corpus; report `paired_mcnemar(zero, gen)` (b=gains, c=regressions) + `bootstrap_paired_delta`. **Never** compare against a stale committed baseline (spike/07.3-06 convention). Run **blind** (bank built without the held-out questions) and **once** per REQ-6.
- **Report lift with AND without near-duplicates** on both shape and entity axes — the delta must survive exclusion (REQ-6 kill condition).

**Adopt bar (all must hold):** shape-coverage ≥70% of held-out failing cases' gold shapes; CK25 net pass-delta > 0 across 3 runs, **zero regressions**, delta stays > 0 after overlap-exclusion; QALD non-regression. **Kill** if CK25 delta ≤ 0 post-exclusion, or only one ontology shows any signal.

## Common Pitfalls

### Pitfall 1: Grouped aggregation collapsed into scalar COUNT
**What goes wrong:** treating HAVING/GROUP-BY as "COUNT with a filter" → scalar-COUNT examples distract HAVING cases (the ck25-30 regression). **Avoid:** shape #5 is distinct, with its own retrievable examples and a data-bound threshold. **Warning sign:** a HAVING held-out case regresses when the bank has only scalar COUNT.

### Pitfall 2: Bad ranking attribute (saturation/ties)
**What goes wrong:** an orderable literal is constant/tied across the category (`weight_g` = 20.0 everywhere) → `LIMIT 1` is non-deterministic, the example's answer is ambiguous. **Avoid:** strict-extremum probe (drop LIMIT, read top-2, require rank1 > rank2); drop tied candidates and log. **Warning sign:** verify gate reports a tie.

### Pitfall 3: Hardcoded instance IRIs instead of name-anchoring
**What goes wrong:** emitting `<…dept-41622>` couples the example to a data snapshot AND targets the orthogonal entity-grounding lever, not composition. **Avoid:** always `?x pv:name "V"`. **Warning sign:** a generated query contains an instance-namespace IRI (`prodi:`), not a vocab predicate.

### Pitfall 4: Entity-level leakage the shape audit misses (D-04/D-05)
**What goes wrong:** binding QALD slots from DBpedia entities that appear in gold queries → test answers leak into examples; shape overlap wouldn't catch it. **Avoid:** QALD stays TBox-only / best-effort; entity-overlap axis in the audit; leakage-safe entity-disjoint fillers on CK25. **Warning sign:** entity-overlap report is non-empty.

### Pitfall 5: pyoxigraph on the engine import path (CLAUDE.md rule 5 / D-08)
**What goes wrong:** a top-level `import pyoxigraph` (or importing the eval builder from engine code) drags a test-only dep into `arango_query_core`/`arango_sparql`. **Avoid:** all pyoxigraph imports function-local; the generator lives under `tests/`; Stage 2 promotes only the pure core. **Warning sign:** engine package gains a transitive pyoxigraph path.

### Pitfall 6: Silent shape drop = hidden coverage gap
**What goes wrong:** a hard shape yields 0 and vanishes silently. **Avoid:** per-shape yield is a first-class report entry with a logged drop-reason (D-02). **Warning sign:** shape count < 9 with no report line explaining the missing shape.

### Pitfall 7: Comparing against a stale committed baseline
**What goes wrong:** measuring the generated arm against a historical zero number instead of a fresh same-session zero arm → confounded delta (the exact 07.3-06/07.4 discipline). **Avoid:** always run a fresh zero arm in the same sweep session. **Warning sign:** the sweep reads a `baseline.json` pass-rate as the comparator.
